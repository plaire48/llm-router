# 내장 사이트 위키 품질 개선

이후 서식 텍스트 검색, 중첩 표와 문서 조회 전환의 개선은 [후속 기록](WIKI-FOLLOWUP-2026-09-24.md)에 이어서 정리했다. 아래 검증 수치는 첫 개선 후보의 기록이다.

브라우저 누비의 사용자 검토 Markdown을 찾고 읽는 품질을 개선했다. 내장 사이트 위키는 로컬 문서 기능이며 외부 OpenWiki 엔진과는 별개다. 이번 변경은 외부 OpenWiki 서버나 Office/Desktop 실행기를 수정하지 않는다.

## 재현한 문제와 반영

| 기존 문제 | 반영 |
| --- | --- |
| `휴가신청`으로 `휴가 신청`을 찾지 못하고 반대 방향도 일부 단어만 일치 | 기존 MiniSearch 결과에 한글 사이 가로 공백을 정규화한 어휘 검색을 결합 |
| 코드 블록의 `# 가짜 제목`이 이후 근거의 제목으로 표시됨 | Markdown 구문 트리의 실제 최상위 제목만 사용 |
| Setext 제목과 상위 업무 제목이 사라짐 | 실제 제목 계층을 문맥으로 함께 색인하고 원문 범위를 반환 |
| 긴 표의 마지막 행에 열 이름이 없어 값의 의미를 판단하기 어려움 | 가능한 행 경계에서 나누고 원본 표 머리글을 별도 문맥으로 첨부 |
| 정규화나 머리글 복사 후 본문 범위를 잘못 표시할 위험 | 본문과 문맥 모두 원본 문자열의 UTF-16 반열린 범위로 비교. 원문 앞에 합성 텍스트를 붙이지 않음 |

본문 900자, 추가 문맥 최대 600자, 문서당 최대 64개 본문 구간, 전체 3개 문서/6개 근거를 유지한다. 과도하게 긴 제목/표 머리글은 `truncated`와 `contextTruncated`로 표시한다. 아주 많은 제목 때문에 고정 창을 사용하면 여러 절이 포함됐는지 `mixedSections`로 표시한다. 이러한 경우 모델에 좁혀 읽도록 안내한다. 한 행이나 코드 블록이 900자를 넘으면 나뉠 수 있다. 인용문/목록 안의 중첩 표는 본문으로 보존하지만 별도 표 머리글 문맥을 추출하지 않는다.

검색 점수는 신뢰 확률이 아니다. 한글 어휘 검색은 NFKC와 소문자를 적용한 뒤 한글 사이의 가로 공백만 무시한다. 줄바꿈과 문장부호를 넘어 붙이지 않으며 음절 순서가 다른 단어는 일치하지 않는다. 동의어 추론과 형태소 분석은 지원하지 않는다. 결과를 RRF `1/(60+rank)`로 결합하되 질의 어휘 포함률을 먼저 비교한다. 영어/경로 식별자는 기존 MiniSearch 경로를 유지한다.

파싱 결과는 마지막 사이트/제공자의 유효한 문서 집합 한 개만 메모리에 보관한다. 다음 검색마다 먼저 권한 범위와 만료를 적용하고 URL/제목/버전/구조/유효 본문을 정확히 비교한다. 같은 버전의 본문 편집도 감지하며 삭제/비활성화/만료/검토 철회/다른 제공자에서 이전 조각을 조회하지 않는다. 디스크 색인을 만들지 않으며 worker 재시작 시 원본으로 재구성한다. 반환한 문맥 객체를 호출자가 바꿔도 캐시가 변하지 않는다.

## 오픈소스와 방법론 비교

2026-09-24 공식 문서와 실제 소스를 확인했다. 후보 전체를 설치하는 대신 현재 실행 환경과 재현된 문제에 맞는 부분을 선택했다.

| 후보 | 적합성, 라이선스와 비용 | 결정 |

| [Microsoft RRF 설명](https://learn.microsoft.com/en-us/azure/search/hybrid-search-ranking) | 서로 다른 점수 척도 대신 검색 순위를 결합하는 방법론 | **순위 결합 공식 적용**. 두 경로 모두 로컬 어휘 검색이며 Azure 서비스/벡터 검색은 사용하지 않음 |

추가 모델 호출, 외부 검색 색인, 라우터 설치가 필요 없다. Markdown은 파싱만 하며 실행하지 않는다. 직접 버전을 고정한 3개 패키지는 기존 설치 트리의 동일한 버전이다. 서비스 워커용 번들은 `worker` export 조건으로 DOM 없는 entity decoder를 선택한다. 기본 `browser` decoder는 `document.createElement`를 사용하므로 그대로 서비스 워커에 넣을 수 없다. 이 경계는 실제 Chrome 검사를 추가했다.

## 검증과 한계

수정 전에 새 6개 회귀 검사를 현재 구현에 실행해 **1개 통과/5개 실패**를 기록했다. 수정 후 같은 6개가 통과했으며 Unicode/CRLF, 긴 문맥 잘림, 전체 원문 포함, 캐시 무효화, 반환 객체 변경 격리 검사 5개를 추가했다. 이는 고정 회귀 사례의 결과이며 일반 정확도 점수가 아니다.

12,029자 합성 문서 200개를 사용한 이 Mac의 Node 단일 측정에서 기존 분할 검색은 122ms, 구조 파싱을 매번 하는 첫 구현은 2,126ms였다. 파싱 재사용 후 첫 검색은 1,930ms, 이어진 3회 검색은 105/105/102ms였다. 20개 문서는 첫 247ms, 후속 13/12/12ms였다. 첫 구조 파싱 비용은 남는다. 이 값은 작은 로컬 표본이며 실제 브라우저 지연 분포나 실모델 정확도 수치가 아니다. 원본은 `comparison.json`과 `cache-timing.json`이다.

`tests/wiki-search-browser.mjs`는 실제 패키지의 MV3 서비스 워커에서 parser 실행, 공백 검색, 원문 범위, 버전/제공자/사이트 격리와 새 확장 페이지의 저장 문서 재조회를 검사한다. 기존 위키 작성/질문/저장/갱신/복원과 함께 검증했다.

최종 후보 검증은 단위 **625/625**, 디자인 검사, 후보 빌드와 관련 Chrome 검사 **23/23회** 통과다. 위키 검색/위키 작성/업무 지식/계획 모드/첨부 검색/문맥/양식 응답 유실의 7개 스위트를 각각 새 프로필로 3회, CSP와 채팅을 1회 검사했다. 전체 브라우저 매트릭스가 아닌 관련 범위 검사다. 생산 의존성 audit은 취약점 0개이며 390px 검토 화면도 직접 확인했다. 원본 보고서는 [최종 검증](../verification/pre-release-2026-09-24T08-40-15-195Z/report.json)이다. 첫 파싱 구현의 통과 기록은 `pre-release-2026-09-24T08-35-32-640Z`에 별도로 보존했다.

기존 TTL 30일, 원본 버전, 사용자 검토, 문서 철회, 제공자/사이트 격리와 최종 행동 승인을 유지한다. 검색 결과는 과거 참고 문서이며 현재 화면/저장 성공의 증거가 아니다. 실모델 Qwen 3.8 27B의 업무 답변 정확도와 사내 실계정 검증은 별도다. 도메인 동의어, 문서 사이 의미 연결, 중첩 표 문맥과 큰 문서 집합의 첫 검색 비용은 후속 평가 대상이다.

근거: `verification/wiki-quality-2026-09-24/`의 수정 전 원본, baseline.log, focused.log와 최종 요약. 후보 ZIP은 `verification/`에만 생성하며 기존 배포 파일을 교체하지 않는다.
