# 브라우저 누비 재검증

2026-09-24. 최근 OpenWiki 위임 변경을 포함해 최종 검토, 복구, 폼 입력과 위키 연결을 다시 확인했다. 선정한 11개 시나리오 묶음 23회, 보완 후 4회 브라우저 검사를 모두 통과했다. 마지막 단위 검사는 675개 통과했다. 전체 브라우저 매트릭스를 실행했다는 뜻은 아니다.

## 확인한 결과

- browser-wiki, form-workflow, harness-repair, completion-review, review-context, output-recovery를 각각 새 프로필로 3회 실행했다. 실패 후 통과할 때까지 재시도하는 방식이 아니다.
- OpenWiki 에이전트, 폴더 등록/해제/원문 변경/페이지 초안 입력, 폴더 유지, CSP와 기본 브라우저 흐름을 실행했다. 실제 브라우저와 합성 페이지/모델 응답을 사용했다.
- 운영 의존성 `npm audit --omit=dev --json` 결과는 검사 당시 알려진 취약점 0건이다. 전체 보안 감사 또는 취약점이 없다는 보장은 아니다.
- 별도 실모델 평가용 환경 변수와 프로젝트 `.env` 계열에서 NUBI_EVAL_TOKEN 설정을 확인하지 못했다. 기존 로그인 저장소에서 인증을 가져오지 않았다. 실제 Qwen의 업무 정확도와 사내 SSO는 이번에 검증하지 않았다.

## 추가 반영

| 문제 | 수정과 검증 |
| --- | --- |
| 검증 중 테스트/의존성은 비교하지만 일부 브라우저 probe가 다시 번들하는 현재 소스와 공유 OpenWiki 코드는 비교 대상에서 빠짐 | `verification-inputs.mjs`로 확장 루트 코드, src/public/scripts/tests/design/vendor 및 공유 OpenWiki/A2A 소스와 잠금 파일을 해시화. dist가 그대로여도 소스/공유 코드 변경을 감지한다. 생성물/검사 로그/인증 파일은 입력에서 제외한다. 선택한 입력 경로의 일관성 검사이며 설치된 node_modules 전체의 무결성 검사는 아니다. |
| 실모델 평가가 요청 발송만으로 actualModel을 표시함 | 제공자 origin/endpoint/POST/선택 모델을 확인한 요청의 응답을 제품의 `readCompletion`으로 검사. 유효한 JSON/SSE/도구 응답 수만 저장한다. 원문과 인증값은 새 기록에 남기지 않는다. 응답 관찰은 5초 안에 마무리하며 늦거나 확인 불가능한 응답은 검증 근거로 인정하지 않는다. |
| 인증 오류만 받은 실패도 실제 모델 정확도 계산에 들어갈 수 있음 | 모든 계획 trial에 검증한 모델 응답이 있어야 점수를 산출한다. HTTP 401, HTML 로그인 화면, 빈/오류 응답, 끊긴 스트림, 불가능한 응답 수와 과거의 응답 수 없는 기록은 점수 미산정이다. 유효한 응답을 받은 뒤 업무에 실패한 trial은 계속 실패로 계산한다. |

유효한 모델 응답은 답변의 사실성이나 도구 실행 성공을 뜻하지 않는다. 실제 페이지 비교/원본 보존/요구사항 검사를 별도로 유지했다. 평가 응답 검사 자체도 Playwright 브라우저에서 401 한 번과 정상 합성 응답 한 번을 보내, 요청 2개/유효 응답 1개/미확인 응답 1개로 분리됨을 확인했다.

## 방법론과 오픈소스 선택

- [Playwright 확장 검사](https://playwright.dev/docs/chrome-extensions): 기존 번들 Chromium과 persistent context를 재사용했다. 테스트 전용 프로필을 쓰고 사용자 설치본을 교체하지 않는다. Playwright의 브라우저 이벤트를 재사용해 평가 요청과 응답을 연결했다.
- [Playwright 반복/실패 구분](https://playwright.dev/docs/test-retries): 성공한 시나리오를 새 프로필로 반복하고 실패를 숨기지 않는 기존 정책을 유지했다. 이번에는 모든 선정 시나리오가 첫 시도부터 통과했다.
- [Anthropic 에이전트 평가 방법론](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents): 시험 환경/실행 기록/관찰 결과와 점수 산출 전제를 분리하는 원칙을 참고했다. 공개 벤치마크 점수나 실제 사내 업무 성공률로 환산하지 않는다.
- 기존 제품의 응답 파서와 Node crypto를 재사용했다. 별도 응답 파서, 평가 서버, 신규 런타임 의존성을 추가할 필요가 없었다. 검색/에이전트 프레임워크 버전 교체보다 재현된 검증 누락을 수정하는 것이 이번 범위에 적합했다.
