# 같은 LLM을 사용하는 위키별 OpenWiki 조회 실행기

후속 검색/미열람 보완/합성 재조회/최종 검토 개선은 [컨텍스트 품질 기록](OPENWIKI-CONTEXT-QUALITY.md)을 따른다.

2026-09-24. 내장 위키와 등록한 외부 위키는 서로 다른 지식이다. 두 문서 집합을 합치지 않고 각각 독립된 실행기에게 질문한다. 모델과 로그인 연결만 현재 누비의 선택을 공유한다.

```text
누비의 현재 질문과 현재 선택 모델
  ├─ ask_openwiki(internal) → 내장 위키 실행기 → 내장 근거와 답변
  └─ ask_openwiki(external) → 외부 위키 실행기 → 외부 근거와 답변
누비가 wikiId를 유지해 비교 → 필요한 브라우저 작업 → 실제 결과 검증
```

`packages/openwiki/src/agent/wiki-question.ts`에 브라우저에서 실행할 수 있는 읽기 전용 DeepAgents 조회 코어를 추가하고 확장에 번들했다. 이전 내장 위키는 검토된 사이트 문서를 저장하고 검색하는 기능이었다. 이번 코어가 실제 모델 호출, 문서 도구 사용, 독립 하위 조회, 결과 합성을 수행한다. OpenWiki CLI 전체나 기존 CLI 채팅 실행기를 그대로 브라우저에 넣은 것은 아니다. CLI의 Node 파일시스템, 셸, 인증 환경과 저장소 수정 기능은 이 조회 코어의 범위가 아니다.

## 연결과 출처

| 대상 | 문서 수집 | 실행과 모델 |
| --- | --- | --- |
| 내장 위키 | 현재 대상 탭의 origin, 현재 제공자, 사용자 검토 버전과 유효 시각으로 한정한 확장 저장 문서 | 요청마다 독립 DeepAgent 문맥. 현재 누비 제공자와 모델 |
| 외부 폴더 | IndexedDB에 저장한 읽기 전용 핸들. 선택 프로젝트의 `openwiki` 하위로 한정 | 내장 위키와 별도 문맥. 같은 현재 모델 |
| 외부 로컬 서버 | 기존 페어링 세션의 인증된 `GET /api/nubi/v1/wiki/snapshot`. 서버가 공개한 Wiki 범위만 수집 | 서버는 문서만 전달. 모델 호출은 누비의 기존 연결 |

별도 OpenWiki 로그인, API key, Node/Python/라우터 설치를 요구하지 않는다. 기존 AI Pro/ChatGPT/FabriX 전송과 추론 복구를 `completeAnalysis`로 재사용한다. 모델 내부의 `search_wiki`/`read_wiki`는 출처별 메모리 스냅샷만 읽는다. 기본 DeepAgents 파일/셸/재귀 위임 도구는 모델 도구 목록과 실행 미들웨어 양쪽에서 거부한다. 문서 내용은 지침이나 승인으로 취급하지 않는다.

폴더 방식이 기본이다. 선택 서버는 `wiki_snapshot` 기능을 알리는 새 코드가 필요하다. 오래된 서버에는 업데이트 또는 폴더 선택을 안내하며 어휘 검색으로 조용히 대체하지 않는다. 기존 서버의 `wiki/query`, `wiki/search`, Wiki/소스 읽기 API는 다른 소비자를 위해 유지한다. 서버의 `sourceComplete`는 현재 그래프의 허용 문서 범위에 관한 값이며 디스크의 모든 미색인 파일까지 포함한다는 뜻이 아니다.

## 긴 문서와 검색 품질

질문을 독립된 측면으로 나누고, 전체 요약/전수 검토 요청은 UTF-16 기준 최대 24,000자 구간을 모두 작업 큐에 넣는다. 한 번에 두 연구자가 처리하며 각 연구자는 새로운 문맥을 가진다. 특정 사실을 찾는 요청은 관련 범위를 검색한다. 긴 문서에 질문 하나만 계획됐으면 반례와 다른 표현을 찾는 연구자를 추가한다. 특정 사실 검색의 성공을 전체 문서 검토 완료로 표현하지 않는다.

검색은 기존 `wikiChunks`와 `rankWikiEvidence`를 재사용한다. Markdown AST 본문, 제목/표 머리글 문맥, MiniSearch와 한글 가로 공백 보완의 RRF 결합을 두 출처 모두에 적용한다. 검색 후보 범위는 실제 읽기를 대신하지 않는다. 연구자는 한 번에 최대 6,000자를 읽고 관찰한 근거 ID만 보고서에 인용할 수 있다. 원문은 정규화하지 않으며 SHA-256과 정확한 UTF-16 범위를 반환한다. 소스 파싱은 검색할 때 시작하고 문맥별 캐시만 사용한다.

하위 보고서는 네 개씩 계층적으로 합친다. 합성 요청에는 길이가 제한된 원문 발췌와 잘림 표시를 전달하며 최종 인용에는 실제 읽은 원문을 보존한다. 합성 실패 시 완료한 하위 조회를 다시 실행하지 않고 검증된 보고서와 합성 미완료 표시를 반환한다. 부분 실패, 수집 제한과 읽지 않은 구간은 전체 완료로 승격하지 않는다. 하위 작업 상태는 실제 시작/종료 이벤트로 표시한다.

반환 직전에 같은 연결로 문서 집합 전체를 다시 읽고 ID, 본문, 버전, 제목, 경로와 종류를 비교한다. 마지막 인용에 포함되지 않은 문서라도 바뀌면 결과를 거부한다. 압축 시 wikiId와 문서 해시/범위를 보존하므로 두 위키의 동일 파일명이 섞이지 않는다. 위키 근거는 정보 답변이나 초안의 참고 자료이며 현재 페이지 입력, 저장 또는 승인 증거가 아니다. 페이지 입력 뒤에도 참고 원문을 화면 관찰과 구분해 유지한다.

| [Anthropic 병렬 연구](https://www.anthropic.com/engineering/multi-agent-research-system) | 독립 범위, 근거 전달, 계층적 합성과 비용 관리 원칙 참고. 해당 시스템 전체를 도입하거나 공개 성능 수치를 누비 성능으로 사용하지 않음 |
| [Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval) | 실제 제목/표 문맥 보존과 질의 보완을 적용. 임베딩, 원격 벡터 DB, LLM 생성 청크 설명은 추가하지 않음 |

버전과 하위 의존성 라이선스는 잠금 파일과 후보 `script-licenses/documents` 기록으로 확인한다. 추가 모델 호출과 약 1.9 MB의 압축 전 UI JS 묶음 비용이 있다. 위키 크기와 질문 복잡도에 따라 모델 비용/시간이 증가한다. 기본 LLM의 실제 컨텍스트/동시 요청 한도는 제공자 전송 경로가 적용한다.

## 제한과 검증

- 요청당 최대 300문서, 문서당 400만자, 합계 800만자. 폴더 수집은 32 MiB/20초와 기존 디렉터리 순회 제한을 유지한다. 제한으로 빠진 문서는 `sourceComplete: false`다.
- 연구자 호출의 그래프 재귀 제한은 48이다. 실패는 미검증 작업으로 남는다. 브라우저 종료 후 하위 작업 자동 재개나 영구 작업 DB는 구현하지 않았다.
- 최종 요구사항 검토는 위키 결과의 원문 근거를 최대 320,000자까지 보존하고 기존 선택 모델 문맥 예산 검사를 적용한다. 예산에 못 들어가는 위키 비교 근거를 조용히 제거하지 않으며 검토 실패로 남긴다. 다른 화면 관찰의 14,000자 제한은 유지한다.
- 실제 DeepAgents를 호출하는 합성 모델 검사: 위키 분리, 같은 모델, 긴 문서의 모든 구간, 120만자 단일 행의 끝, 미열람 구간, 허위 인용, 기본 파일 도구 차단, 취소, 합성 실패 보존, 비인용 문서 변경 거부.
- 실제 Chrome 5개 흐름, 확장 테스트 650개, OpenWiki API 테스트 10개, TypeScript 검사와 CX 디자인 검사 통과. 이 검사는 실계정 Qwen/AI Pro/ChatGPT/FabriX의 답변 정확도나 지연을 입증하지 않는다.

구현 전 잠깐 준비했던 서버 에이전트 작업 경로는 제거했다. 주 에이전트의 직접 위키 검색 도구를 `ask_openwiki`로 통일했고, 기존 소스 API와 위키 작성/검토/저장 흐름은 계속 사용한다.


검증 원본: [결과와 후보 해시](../verification/openwiki-delegation-2026-09-24/report.json). Chrome 검사는 내장 위키 생성/검토/저장/재조회, 외부 폴더 등록/재진입/변경 읽기/초안 입력, 실제 로컬 서버의 페어링/읽기/해제/종료, 현재 화면과 소스 비교, 서비스 워커의 두 위키 격리와 현재 모델 연결을 포함한다. 외부 폴더 검사는 실제 File System Access 핸들과 IndexedDB, 실제 페이지 입력과 readback을 사용하고 모델 응답만 고정했다. 320/360/1100px 설정 검사와 생성된 초안 화면도 확인했다. 배포 후보만 만들었으며 공개 릴리스나 설치된 사용자 확장 갱신을 완료했다고 주장하지 않는다.
