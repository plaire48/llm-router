# 누비 탭 재사용

## 확인한 원인

- 전체 화면 열기 `OPEN_TAB`은 기존 누비 화면을 조회하지 않고 매번 탭을 생성했다.
- 실제 Chrome 재검사에서 `tabs` 권한 없이 `tabs.query()`가 확장 페이지 URL도 숨기는 것을 확인했다. URL 목록 기반 첫 수정은 기존 탭을 놓쳤으며 `runtime.getContexts()`의 실제 확장 `TAB` 문서와 tab ID를 대조하는 방식으로 고쳤다.
- 현재 페이지 연결 `CONNECT_PAGE`는 같은 대화의 누비 작업 탭 또는 원본을 다시 연결해도 작업 공간 소유권을 삭제했다. 다음 도구 실행은 기존 초안 대신 새 복제 탭을 만들었다.

## 반영

- 일반 `index.html` 누비 화면이 열려 있으면 해당 탭과 창을 활성화한다. 화면을 새로고침하지 않아 입력 초안을 유지한다. 명시적인 설정 열기는 대상 탭 ID에 보낸 `NUBI_OPEN_VIEW`로 처리한다. 다른 대화의 이력을 지정한 query deep link와 시크릿 창은 후보에서 제외한다.
- 동일 대화, 제공자, 인증 시점에 연결된 실제 소유 탭이나 그 원본을 재연결하면 작업 공간을 유지한다. 소유 탭을 직접 선택했다면 그 탭이 다음 관찰 대상이 된다.
- URL이나 그룹 이름만으로 탭을 인수하지 않는다. 다른 문서를 명시적으로 연결하거나 계정/대화가 다르면 기존 연결을 재사용하지 않는다. 닫힌 탭과 다른 창으로 옮겨진 탭은 재사용하지 않는다.
- 권한, 승인, 쓰기 재개 경계는 바꾸지 않는다. 재연결은 DOM 재관찰이며 기존 ref나 완료 증거를 재사용하는 동작이 아니다.

## 방법론과 선택

Chrome 공식 [Runtime contexts API](https://developer.chrome.com/docs/extensions/reference/api/runtime#method-getContexts)로 확장 자신의 최상위 탭 문서를 조회하고 [Tabs API](https://developer.chrome.com/docs/extensions/reference/api/tabs)와 [Windows API](https://developer.chrome.com/docs/extensions/reference/api/windows)의 `active`/`focused` 분리 동작을 적용했다. URL 조회를 위한 `tabs` 권한을 추가하지 않는다. 화면 활성화와 작업 실행 권한을 구분하고 기존 세션 소유권 검사를 재사용했다. 이번 탭 수명 문제는 브라우저 기본 API로 해결할 수 있어 별도 에이전트/창 관리 라이브러리는 추가하지 않았다. OpenCode/Codex의 워커/문맥 관리와는 독립된 호스트 UI 및 탭 소유권 문제다.

## 검증

- `node --test tests/browser-workspace.test.mjs`: 9개 통과. 기존 탭 활성화, URL/초안 유지, URL이 숨겨진 Chrome 권한 조건, 새 탭이 필요한 경우, 같은 소유 탭/원본 재연결, 다른 소유권/닫힘/이동 거부를 확인했다.
- 실제 Chrome 회귀에 `workspace-flow-browser.mjs`의 같은 작업 탭/원본 재연결 후 초안 유지와 `page-skills-browser.mjs`의 전체 화면 중복 방지 검사를 추가했다. 최종 후보에서 두 스위트가 통과했고 설정 재열기 두 번도 같은 문서/탭을 유지했다.
- 합성 브라우저 검사는 실계정 모델의 업무 완료 품질을 증명하지 않는다. 기존 Chrome 프로필의 사용자 탭은 임의로 닫거나 정리하지 않는다.
