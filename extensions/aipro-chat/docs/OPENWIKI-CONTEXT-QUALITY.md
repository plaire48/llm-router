# OpenWiki 긴 문서와 합성 품질 보완

2026-09-24. 내장 위키와 외부 위키의 독립 실행, 현재 누비 LLM 연결 공유는 유지한다. 이번 변경은 검색 후보, 미열람 구간 보완, 합성 문맥에 적용한다. 실계정 모델 정확도를 측정한 기록은 아니다.

## 확인한 문제와 반영

| 문제 | 적용 |
| --- | --- |
| 한 문서의 반복 구간이 검색 후보 8개를 독점할 수 있음 | 기존 MiniSearch/Markdown/RRF 순위에서 문서별 2개를 우선 배치하고 남은 칸을 채움. 다른 문서의 예외 규정도 후보로 비교. 순위를 의미적 정확도로 표현하지 않음 |
| 연구자가 6,000자만 읽고 답하면 나머지는 미열람으로 끝남 | 원래 질문과 남은 범위만 새 하위 문맥에 전달. 실제로 미열람 범위가 줄어드는 동안 계속 보완. 진전이 없으면 해당 보완을 멈추고 남은 범위를 반환 |
| 합성에는 읽은 근거의 앞 800자만 전달되어 뒤의 사실이 사라짐 | 질문과 해당 근거를 인용한 결론으로 MiniSearch 미리보기 선정. 원문 기준 excerptStart/End 반환. 합성 실행기가 해당 보고서 묶음의 근거 ID만 `read_wiki`로 재조회 가능 |
| 여러 보완 보고서를 한꺼번에 합치면 문맥이 커짐 | 보완 결과와 전체 결과 모두 4개씩 계층적 합성. 보완과 합성도 원래 두 작업 슬롯 안에서 수행 |
| 중간 합성 실패가 다음 모델의 complete 선언으로 덮일 수 있음 | synthesisFailures를 호스트가 유지. 부분 상태와 미해결 항목을 다음 합성에 보존. 최종 모델의 선언으로 실패를 지울 수 없음 |
| 긴 위키 근거가 최종 검토의 14,000자 고정 제한에 걸림 | 위키 결과는 최대 320,000자까지 원문 보존 후 기존 선택 모델 문맥 예산 검사. 여러 위키의 비교 근거를 하나씩 조용히 제거하지 않으며 예산 부족 시 검토 미완료 |
| 빠르게 끝난 하위 결과 순서가 합성 입력 순서를 바꿈 | 원래 작업 순서대로 보고서를 배치. 완료 시간에 따라 입력 순서를 바꾸지 않음 |

미열람 보완은 성공한 범위를 다시 읽지 않는다. 각 새 연구자는 자신의 실제 읽기에서 생성된 인용 ID만 사용할 수 있다. 합성 재조회는 이미 해당 묶음에 인용된 스냅샷 범위에 한정한다. 다른 위키, 임의 파일, 셸과 브라우저 작업으로 확장하지 않는다. 모든 읽기의 원문 범위와 해시, 반환 전 전체 문서 변경 검사는 유지한다.

`coverage.repairTasks`는 추가 하위 조회 수, `synthesisFailures`는 합성 실패 수다. 실제 원문을 읽었다는 사실과 해석 성공을 구분하며, 부분 읽기 연구자의 진행 표시는 partial이다. 수집 제한으로 제외된 문서는 읽기 보완으로 되살릴 수 없으므로 sourceComplete:false를 유지한다. 브라우저 종료 후 복구나 영구 작업 저장소는 이번 범위가 아니다.

| 후보 | 판단 |

| [p-limit](https://github.com/sindresorhus/p-limit) | MIT. 이미 누비의 다른 경로에서 사용. 이번 코어의 두 작업 소비자는 보완/합성까지 같은 슬롯을 유지하므로 새 의존성이나 별도 큐로 교체할 이득이 없어 유지. 실제 동시 호출 상한을 테스트 |
| FlexSearch / 벡터 검색 / MMR | 이전 비교의 전제 유지. 이번 결함은 검색 엔진 종류보다 후보 편중, 미열람 처리와 합성 근거 누락에 있음. 임베딩 기반 MMR을 구현했다고 주장하지 않으며, 문서별 후보 배치만 적용. 의미 검색 도입은 실제 질문 정답셋 평가 후 판단 |

설계 패턴 적용과 패키지 도입을 구분했다. 이번 변경은 새 런타임 의존성을 추가하지 않는다. 검색 후보 다양성은 항상 정확도를 올린다는 보장이 없으며, 반환 원문과 모델 검토가 필요하다.

## 검증

추가 회귀 검사는 다음을 확인한다.

- 근거의 앞 800자에는 없는 뒤쪽 사실이 새 미리보기에 포함되고 원문 offset과 일치한다.
- 합성 DeepAgent가 도구를 호출해 생략된 원문을 읽는다. 다른 근거 ID와 범위 밖 읽기는 거부한다.
- 55,000자 문서를 매번 일부만 읽는 모델에서도 미열람 구간이 자동으로 줄어든다. 완료한 범위는 재실행하지 않는다.
- 진전 없는 보완은 한 번 확인한 뒤 남은 범위를 반환한다. 읽기 진행이 계속되면 횟수만으로 끊지 않는다.
- 작은 범위로 반복 보완해도 동시 모델 호출 2개, 합성 묶음 4개를 넘지 않는다.
- 중간 합성 실패 뒤 다음 합성이 성공해도 최종 partial과 실패 수가 유지된다.
- 긴 일반 규정과 별도 예외 규정이 있을 때 둘 다 검색 후보에 남는다.

Chrome 검사는 실제 확장 서비스 워커에서 내장 문서와 약 54,600자 외부 문서를 별도로 위임하고, 외부 문서의 미열람 구간을 보완한다. 모델 응답은 고정했다. 선택 모델의 문맥 검사는 기존 contextTokens 추정을 사용하며 실제 제공자 입력 한도를 새로 측정한 것은 아니다. 실제 모델의 의미 검색 정확도, 사실성, 지연과 사용량은 아직 미측정이다. 결과와 로그는 `verification/openwiki-quality-2026-09-24/`에 기록한다.

최종 검증: 전체 **658개 통과**, 이번 회귀 **8개 추가**, OpenWiki 코어 22개와 TypeScript 검사 통과. Chrome 151에서 약 54,600자 외부 문서의 추가 조회 7개와 미열람 0을 확인했다. 폴더 등록/재진입/현재 모델 위임/실제 페이지 초안 입력과 검증도 통과했다. 모델 응답은 합성 데이터다. [원본 로그와 후보 해시](../verification/openwiki-quality-2026-09-24/report.json)를 참고한다. 후보 ZIP만 생성했고 배포하지 않았다.

## 후속 검토: 구조 문맥과 긴 Markdown 처리

같은 날짜의 후속 검사에서 다음 두 가지를 추가 반영했다. 앞 절의 658개 검사는 이전 단계 기록이며 이번 전체 검사는 **660개 통과**다.

- 검색 순위에는 상위 제목과 표 머리글을 사용하면서 실제 OpenWiki 검색 도구에는 본문 범위만 전달하던 누락을 수정했다. `contextRanges`에 원문 제목/머리글 위치를 반환한다. 에이전트가 해당 범위를 `read_wiki`로 읽어야 인용 ID가 생긴다. 원문을 읽지 않은 검색 결과를 근거로 승격하지 않는다.
- 담당 범위 밖 머리글은 읽기 권한을 넓히지 않고 `contextUnavailable`로 알린다. 잘린 문맥과 여러 절이 섞인 조각도 별도 표시한다. 범위 밖 문맥까지 자동으로 해석을 완료한다고 보장하지 않는다. 외부 검색 구현이 잘못된 문서 ID, 숫자 범위나 임의 메타데이터를 반환해도 도구가 검증하고 제거한다.
- Markdown AST의 순서 있는 위치 정보를 재사용해 텍스트 노드, 구간 경계, 제목과 표를 이진 탐색한다. 조각마다 전체 노드를 다시 훑던 비용을 줄였다. 원문 조각, 검색 텍스트, 부모 문맥과 위치는 변경 전과 동일하다.

### 선택 근거

[Anthropic Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval)의 조각별 문맥 보존 원칙을 참고했다. 이 구현은 원문에 존재하는 제목과 열 이름만 사용하며, 논문의 LLM 문맥 생성, 임베딩, Contextual BM25 전체 파이프라인이나 발표된 정확도 수치를 도입한 것은 아니다. 기존 [mdast-util-from-markdown](https://github.com/syntax-tree/mdast-util-from-markdown) 2.0.3의 AST 위치 정보와 GFM 파서, [MiniSearch](https://github.com/lucaong/minisearch) 7.2.0을 재사용했다. 설치 소스와 MIT 라이선스를 확인했다. 패키지와 네트워크 호출을 추가하지 않았다.

FlexSearch로의 교체는 이번 원인이었던 도구 전달 시 문맥 누락을 해결하지 않는다. 별도 임베딩/재순위 서비스는 인증, 지연, 비용과 실계정 평가가 필요하므로 이번에 추가하지 않았다. 긴 문서의 실제 하위 실행은 기존 DeepAgents/LangChain과 두 작업 슬롯을 유지한다.

### 검증과 한계

- 660개 전체 테스트, OpenWiki TypeScript 검사, 후보 빌드 통과. 검색 머리글의 원문 일치, 검색만으로 인용이 생기지 않음, 할당 밖 읽기 차단과 잘못된 검색 메타데이터 차단을 추가 검사했다.
- 실제 Chrome 151 서비스 워커에서 긴 표의 뒤쪽 항목을 검색한 후 멀리 있는 열 이름 `원/일`을 원문으로 읽었다. 같은 검사에서 두 Wiki 분리, 동일 모델 ID, 읽기 전용 도구, 54,600자 외부 문서 보완과 미열람 0을 재확인했다. 29회의 모델 응답은 합성 데이터다.
- 약 155만 자, 2,148개 조각의 단일 로컬 실험: 변경 전 10,578ms, 변경 후 2,770ms. 3만/30만/155만 자 결과를 전체 비교해 일치했다. 추가로 중첩 표, 링크, HTML, 코드, Unicode와 겹치는 구간 8개 사례도 일치했다. 이 수치는 단일 환경의 처리 시간이며 실계정 지연이나 평균 성능 보장이 아니다.
- 재현: `node scripts/evaluate-wiki-structure.mjs`. [실험과 검사 기록](../verification/openwiki-structure-2026-09-24/report.json). 기존 번들 크기 경고는 남아 있다. 후보 ZIP만 생성했으며 사용자 설치본 교체나 배포는 하지 않았다.

## 후속 검토: 분할 경계를 넘는 구조 문맥

이전 단계의 검색 위치 제공만으로는 전체 문서 읽기를 충분히 돕지 못했다. 24,000자 뒤쪽을 담당하는 연구자는 검색 없이 직접 본문을 읽을 수 있고, 앞쪽의 표 머리글은 일반 읽기 범위 밖이기 때문이다. 이번에는 본문 읽기에 원문 구조 문맥을 자동으로 보완했다.

- 기존 Markdown AST/검색 캐시에서 읽는 구간에 연결된 제목과 표 머리글 위치를 얻는다. 호스트가 같은 스냅샷의 원문을 최대 600자, 최대 12개 범위로 제한하고 `contextEvidence`로 반환한다. 모델이 지정한 다른 문서나 생성한 요약을 사용하지 않는다.
- 보완 원문마다 본문과 같은 문서 ID/해시/버전, 별도 원문 offset과 인용 ID가 붙는다. 하위 연구와 계층적 합성이 그 인용을 보존할 수 있다. 긴 제목/열 이름이 잘리거나 구조 파싱이 실패하면 `contextTruncated`를 표시한다. 파싱 실패가 성공한 본문 읽기를 지우지 않는다.
- 직접 `read_wiki`는 여전히 담당 범위 밖을 거부한다. 머리글이 제공되어도 그 사이 본문을 읽은 것으로 처리하지 않는다. 미열람 계산은 담당 문서와 범위의 실제 교집합만 사용해 다른 구간으로 보완 작업이 새어나가지 않는다.
- 반복되는 구조 문맥은 각 새 하위 실행에도 제공한다. 이는 이미 읽은 본문을 다시 실행하는 것과 구분한다. 문서 내용/제목이 달라지면 검색 조각과 구조 문맥 캐시를 함께 갱신한다.

[DeepAgents의 독립 하위 문맥](https://docs.langchain.com/oss/javascript/deepagents/subagents)과 [Anthropic의 필요한 근거를 선택적으로 가져오는 문맥 관리](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)를 참고했다. DeepAgents/LangChain의 기존 읽기 전용 루프와 MDAST/GFM 파서를 실제 재사용하며 추가 패키지나 모델 호출은 없다. 전체 부모 대화 복사와 무제한 문서 확장은 문맥 혼합 및 비용을 늘리므로 적용하지 않았다. 공개 방법론의 성능 수치를 이 제품의 검증값으로 사용하지 않는다. 제목/표 머리글 보완은 문서 전체의 예외 조건을 자동으로 완전히 해석한다는 보장이 아니다.

이번 검증은 **665개 전체 테스트**, 코어 29개, OpenWiki TypeScript 검사와 후보 빌드를 통과했다. 추가 5개 회귀는 긴 표의 단위 자동 제공/인용 유지, 다른 문서와 할당 밖 직접 읽기 차단, 600자 예산/파싱 실패, 검색 캐시 갱신, 분할 밖 문맥의 읽기 완료 오인 방지를 확인한다. 실제 Chrome 서비스 워커에서도 뒤쪽 구간의 구조 문맥 자동 제공, 동일 모델 연결, 내장/외부 Wiki 분리와 기존 긴 문서 보완을 확인했다. 모델 응답은 고정한 합성 데이터이며 실제 Qwen 계정의 정확도/지연/비용 평가는 아직 미측정이다. [검증 로그와 후보 해시](../verification/openwiki-boundary-2026-09-24/report.json)를 남겼다. 배포와 사용자 설치본 교체는 수행하지 않았다.

## 후속 검토: 계층적 합성의 재검색과 빈 검색 결과 전달

중간 요약에서 빠진 원래 하위 결론과 인용은 다음 합성에서 접근할 수 없었다. 실행 안에 원래 하위 결론/미해결 항목과 인용 ID를 보관하고, 각 합성에 속한 하위 분기만 MiniSearch로 검색하도록 보완했다. 합성용 `search_wiki`는 최대 8개 연구 메모를 반환하고 `read_wiki`는 그 분기의 관찰된 원문 인용을 읽는다. 메모는 모델의 주장으로 표시하며 원문 사실과 구분한다. 모든 원문을 매번 프롬프트에 넣지 않는다. 합성 실패 시에도 원래 하위 메모의 연결은 유지한다. 저장소는 해당 질문의 메모리에만 존재하며 영구 저장/재시작 복구 기능이 아니다.

회귀 검사 과정에서 **빈 검색 배열이 모델 전송에서 빈 문자열로 변하는 문제**도 재현했다. 설치된 LangChain/core의 `_formatToolOutput`는 빈 배열을 콘텐츠 블록 배열로 허용하고, 누비의 텍스트 추출 결과는 빈 문자열이 된다. 검색 도구가 명시적인 JSON 문자열을 반환하게 해 `[]`와 실제 검색 후보를 모두 보존했다. 빈 결과는 검색 실패/자료 부재의 증명이 아니며 모델이 다른 검색어나 원문 조회로 이어갈 수 있다. 이 수정은 일반 검색과 합성 검색 모두에 적용한다.

[LangChain 도구 반환 계약](https://docs.langchain.com/oss/javascript/langchain/tools), [DeepAgents 하위 문맥 분리](https://docs.langchain.com/oss/javascript/deepagents/subagents), [Anthropic의 선택적 문맥 조회/압축](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)을 현재 공식 문서와 설치 소스로 확인했다. 기존 MIT MiniSearch, LangChain/core와 DeepAgents를 실제 재사용했다. 별도 벡터 DB나 영구 메모리 서버는 이번 문제를 해결하는 데 필요하지 않아 도입하지 않았다. 새 런타임 의존성이나 외부 연결을 추가하지 않는다.

검증: **전체 668개 통과**, 코어 32개, TypeScript와 후보 빌드 통과. 추가 검사는 17개 문서의 여러 단계 합성에서 예외가 중간 요약/미리보기에서 빠져도 메모 검색→인용 원문 읽기→최종 인용으로 복구되는지 확인한다. 다른 분기의 메모는 검색되지 않는다. 실제 DeepAgent→누비 모델 변환에서 검색 일치 결과와 `[]`가 모두 파싱 가능함을 별도로 검사했다. Chrome 151 서비스 워커는 문서 검색 11회와 하위 결론 검색 5회, 같은 모델 연결과 Wiki 분리, 외부 긴 문서의 미열람 0을 확인했다. 총 45회의 모델 응답은 합성 데이터다. 실제 모델의 예외 탐지/재검색 선택 능력과 답변 정확도는 여전히 미측정이며 자동 재검색이 모든 누락을 찾는다고 보장하지 않는다.

[로그와 후보 해시](../verification/openwiki-archive-2026-09-24/report.json). 이전 단계의 Chrome 검사는 주로 직접 읽기 흐름이었다. 이번에 모델이 실제 검색을 선택하고 결과를 소비하는 흐름을 추가했다. 기존 번들 크기 경고는 유지하며, 배포/사용자 설치본 변경은 하지 않았다.
