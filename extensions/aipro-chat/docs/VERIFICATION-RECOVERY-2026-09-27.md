# 기술적 검증 실패와 사용자 질문 분리

## 실측 근거

[b4489e E03 감사](../verification/browser-30/b4489e-e03-cause-audit.json)는 클릭 dispatch와 원문 열람이 달랐음을 확인했다. 클릭 두 번 이후에도 검색 화면을 읽었으며 본문 조건과 URL 검사가 실패했다. 49개 모델 호출 중 압축13회가176,829ms를 사용했다. 마지막은 계획0/3, 답변 없음, 본문 확인 범위를 묻는 질문이었다.

저장된 검토는 모두 revise이고 blocked는 없었다. 마지막 모델에 도구 하나만 제공된 기록은 `questionFor`의 강제 질문 경로와 일치한다. 다만 당시 repair counter와 질문 경로 사유 원문을 직접 보존하지 않아 단일 분기를 유일한 원인으로 단정하지 않는다.

## 선택과 반영

[Anthropic의 명확한 도구/오류 계약](https://www.anthropic.com/engineering/writing-tools-for-agents), [문맥 격리와 subagent](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents), 기존 [최종 누락 복구 기록](EASY10-QUALITY-2026-09-27.md)을 재사용한다. 새 프레임워크를 추가하지 않고 Pi와 실행 내 원문 조회, 기존 읽기 전용 recovery 역할을 사용한다.

1. 브라우저 검증 교정 기회를 소진하면 마지막 관찰과 실제 동작 영수증을 읽는 복구 워커를 호출한다.
2. 같은 사용자 요청 revision당 한 번만 허용한다. DOM 변화, 계획 표현, 새 워커 ID로 기회를 늘리지 않는다.
3. 조언을 받은 주 실행기가 실제 관찰과 검증을 수행한다. 조언은 권한이나 완료 근거가 아니며 검증 부채를 지우지 않는다.
4. 여전히 검증하지 못하면 현재 작업을 보존하고 **다시 확인 / 중지**를 묻는다. 명확한 사용자 요구를 다시 설명하라고 하지 않는다.
5. 실제 입력 질문, 승인 대기, 미확정 쓰기와 취소의 기존 경로를 유지한다. 확정하지 못한 쓰기를 재전송하지 않는다.
