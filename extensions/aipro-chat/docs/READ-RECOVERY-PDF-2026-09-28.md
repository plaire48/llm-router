# 브라우저 읽기, 실행 복구, PDF 개선

이 문서는 첫 수정 시점의 기록이다. 이후 열린 PDF 직접 읽기와 계획 범위 교정을 구현한 내용 및 새 후보 결과는 [후속 개선과 재시험](BROWSER-REPAIR-AND-UX-2026-09-28.md)을 따른다.

목표는 페이지를 많이 읽는 것이 아니라 사용자 요청에 필요한 사실을 출처와 함께 전달하는 것이다. 계획 전체 완료, 최종 답변 표시, 독립 정답 검사를 모두 통과해야 성공이다.

## 정보를 빠르고 정확하게 얻기

| 단계 | 적용 방법 | 근거와 한계 |
| --- | --- | --- |
| 필요한 정보 정의 | 요청의 필수 결과와 선택한 조사 방법을 구분한다 | 원문 확인이 필수 아닌 요청에 PDF 원문 열람을 필수 계획으로 추가하면 불필요한 실패가 생긴다 |
| 구조 파악 | 제목, 카드, 표, 링크를 먼저 관찰하고 필요한 영역만 읽는다 | 기존 Mozilla Readability와 읽기 전용 region_ref를 재사용한다 |
| 근거 보존 | 값과 항목 이름, 날짜, URL, 문서 ID를 함께 보존한다 | 숫자만 분리하면 현재 기온과 다른 날짜 예보를 혼동할 수 있다 |
| 긴 문서 분담 | 같은 스냅샷의 독립 구간을 읽기 전용 워커에 나누고 원문 인용과 미확인 범위를 합친다 | 짧은 페이지에도 워커를 늘리면 모델 왕복 비용이 증가한다. 공유 탭의 조작은 순차 실행한다 |
| 최종 확인 | 필요한 항목만 원문과 다시 비교한다 | 새 캡처 ID나 모델의 완료 선언은 새로운 사실 확인이 아니다 |

[Anthropic 문맥 관리](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)의 필요한 정보만 단계적으로 가져오기와 하위 작업 문맥 분리를 적용한다. 기존 Pi, MiniSearch, Mozilla Readability, Playwright와 문서 분할 기능을 우선 사용한다. 모든 페이지를 다중 에이전트에 보내는 구조는 채택하지 않는다.

이번 수정은 시각 복구의 동일 DOM 중복 전달도 제거했다. 합성 입력에서128,756→64,689자로 줄었지만 이 수치를 실제 시간 개선율로 사용하지 않는다.

| 확인한 원인 | 반영 내용 | 검증 상태 |
| --- | --- | --- |
| 화면 전환 뒤 입력 수행 근거 유실 | 일반 fill_form/Enter에도 같은 대상의 입력 영수증을 연결. 검토에만 해시가 일치하는 기존 입력값 보존 | 관련 단위114개, 격리 Chrome7개 통과. 실제 모델 효과 미측정 |
| 취소 후 관찰 오류가 원래 부분 실패를 덮음 | 최초 취소와 부분 실행 기록 유지 | 위 Chrome 검사에 포함 |
| 최종 문장 교정을 브라우저 복구와 같은 재시도로 취급 | 별도 검토가 답변만의 문제로 판정한 경우 도구 없는 교정을 사용자 요구 변경당1회 허용. 이후 독립 최종 검토 필수 | 실제 Pi 회귀5개 통과. 행동 요청 차단, 반복 실패, 취소 포함 |
| 원문이 필수 아닌 요청에서 PDF 경로 고집 | 원래 요구와 방법 구분이 필요한 결함으로 확인 | 미해결. 단순 PDF 미지원 오류 전달만으로 해결되지 않음 |
| PDF 캡처와 오래된 좌표 행동 반복 | 저장용 첨부 ID를 반복 비교에서 제외. 관찰 스크린샷을 문서/뷰포트/호스트 이미지 해시와 연결 | 동일 캡처→실패 클릭5회 반복 누적, 다른 이미지 변화, 취소/미확정쓰기 회귀 통과. 실제 모델 효과 미측정 |

입력 영수증은 검색 성공이나 승인 증명이 아니다. 공개 진단에는 입력 원문을 넣지 않는다. 검토 전용 입력값은 실행 중8,192자 한도로 보존하며 비밀번호, 불명확한 대상, 부분 실패와 취소는 대상에서 제외한다. 이전 대상은 현재 DOM 조작 권한으로 복원하지 않는다.

전체 소스 단위 검사1,249개와 디자인 검사, 임시 출력 경로의 실제 Vite 빌드를 통과했다. ZIP 배포나 전체 Chrome 회귀를 완료한 뜻은 아니다. 새 소스 변경은 실행 중인 고정 후보에 들어 있지 않으며 새 후보 실측이 필요하다.

## PDF 정보 입력 경로

현재 첨부 PDF는 기존 PDF.js로 텍스트를 읽는다. 열린 PDF 탭은 DOM 읽기만으로 본문을 얻을 수 없어 별도 연결이 필요하다. PDF 파일 내용을 모델 문맥에 넣는 것과 PDF 양식에 값을 쓰는 기능은 서로 다른 범위다.

권장 연결은 현재 관찰한 PDF → 문서/접근 권한 확인 → 제한된 원문 가져오기 → PDF.js 페이지별 추출 → 필요한 페이지 검색 → 쪽수와 원문 인용으로 답변이다. [PDF.js 공식 예제](https://mozilla.github.io/pdf.js/examples/)의 getDocument/getPage를 기존 Apache-2.0 의존성에서 재사용할 수 있다.

1. 임의 모델 URL 대신 현재 소유 탭의 실제 관찰 PDF만 읽는다. URL 일치만으로 문서 동일성을 추정하지 않는다.
2. 첫 범위는 공개 HTTP(S) PDF로 제한한다. 리다이렉트, 인증 필요, 크기 초과, 비정상 PDF는 원인을 구분한다.
3. 페이지 번호, 원문 해시, 텍스트 범위와 빈 페이지를 보존한다. 전체를 읽지 않았으면 전체 열람으로 표시하지 않는다.
4. 같은 페이지의 표 제목과 항목 관계를 유지한다. 스캔/도표는 필요한 페이지 이미지와 OCR 또는 이미지 지원 모델을 별도로 검증해야 한다.
5. Chrome은 offscreen 문서를 하나만 허용하므로 기존 이미지 처리와 실행 수명을 공유한다. [Chrome offscreen 문서](https://developer.chrome.com/docs/extensions/reference/api/offscreen).

열린 PDF 직접 추출, 스캔 OCR, PDF 양식 작성은 이번 변경에서 완료하지 않았다. 격리 Chrome에서 로컬 PDF의 실제 document identity 확보, 동일 URL 새로고침 뒤 identity 변경, 기존 권한으로620바이트 원본 가져오기와 해시 일치는 확인했다. [PDF 선행 검사](../verification/pdf-viewer-identity/probe.json). 원격/인증 PDF와 실제 페이지 추출은 검증 전이며 패키지의 Worker 시작 검사도 필요하다. 기존 첨부 파서가 있다는 이유만으로 브라우저 PDF 지원으로 표시하지 않는다.
