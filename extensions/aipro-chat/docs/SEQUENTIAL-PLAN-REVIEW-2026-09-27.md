# 실제 실패에서 단계별 완료 검증으로

## 판단 근거

동일 후보 b4489e의 [E-08 실측 감사](../verification/browser-30/b4489e-e08-cause-audit.json)를 입력으로 삼았다. 모델95회 호출과533,180ms 뒤 계획0/3, 최종 답변 없음으로 끝났다. 통신은95회 모두 HTTP200이었다. 검토43회는192,281ms를 사용했다. 따라서 통신 재시도를 늘리는 것이 직접적인 해결책은 아니다.

보존된 평가 확장의 정확한 캡처 ID로 [당시 PDF 이미지](../verification/browser-30/b4489e-e08-final-capture.png)를 읽기 전용으로 복구하고 직접 보았다. 1/39페이지의 남자 사브르 표에서 오상욱과 대전광역시청을 확인했다. 따라서 DOM0자는 화면에 읽을 정보가 전혀 없다는 뜻이 아니다. 이 이미지로 시험 당일 현재 소속이나 게시일, 나머지38페이지 열람은 입증하지 않는다. [후속 시각 감사](../verification/browser-30/b4489e-e08-visual-followup.json)에 원래 캡처 메타데이터와 파일 해시를 보존했다. 최종 답변이 없었으므로 E-08의 실패 판정은 유지한다.

코드를 대조하니 모델이 도구 호출 없는 후보 답변을 반환할 때 호스트가 모든 미완료 계획을 `stepOutcomes`에 넣고, 전체 통과 전까지 어느 단계도 저장하지 않았다. E-08의 마지막 검토 흐름은 이 경로와 일치하지만 당시 호출 분기 식별자가 없어 유일한 원인으로 단정하지 않는다. 별도의 문제로 원래 요청에 없던 IOC/PDF 필수 경로, 범위 감사 형식 실패, PDF 본문 추출 공백이 남아 있다.

현재 단계 하나만 넘겨야 한다는 회귀 조건을 먼저 추가했다. 수정 전 실제 `runAgent`는3개를 넘겨 실패했다. [수정 전 실패](../verification/sequential-plan/before-unit.log)를 보존했다. 이는 호스트 경로의 인과 재현이며 실제 모델이 같은 판단을 한다는 증거는 아니다.

## 방법론과 반영

[Anthropic의 단계별 연결과 중간 검증](https://www.anthropic.com/engineering/building-effective-agents)을 적용했다. 복잡도를 늘리기 전에 각 단계의 입력과 결과를 분리하고, 실제 환경에서 얻은 근거를 확인한 뒤 다음 단계로 연결한다. 해당 문서의 단계 검증 원칙을 사용했으며 특정 최신 서비스 기능의 동등성을 주장하지 않는다.

기존 Pi 실행기의 follow-up, Nubi의 `reviewGoal`, 영속 `update_plan`을 재사용했다. 별도 다중 에이전트 프레임워크나 새로운 패키지는 도입하지 않았다. 이번 병목은 워커 수가 아니라 호스트가 완료 조건을 묶는 방식이기 때문이다. 상용 Claude 확장의 코드를 복사하지 않았다.

1. 텍스트 후보 뒤 현재 진행 단계 하나를 검토한다. 진행 중 단계가 없으면 첫 미완료 단계를 선택한다.
2. 그 단계가 실제로 통과하면 해당 항목만 완료로 저장하고, 저장된 계획이 요청한 상태와 정확히 같은지 확인한다.
3. 뒤의 단계는 미완료로 유지한다. 실제 저장한 진행 상황을 주 실행기에 전달하고 다음 작업을 계속한다. 이후 단계의 검증 실패가 이미 확인한 단계를 지우지 않는다.
4. 모든 단계가 완료돼도 최종 요청 전체와 답변은 별도로 검토한다. 최종 검토 전 후보 답변은 사용자에게 완료 답변으로 전달하지 않는다.
5. 복구 분석에 현재 단계 범위를 전달한다. 계획 문구만 바꾸어 복구 워커가 두 번 호출되는 추가 허점을 재현했고, 호스트가 실제 검증 완료를 저장했을 때만 증가하는 진전 번호로 바꿨다. 새 근거 없는 문구 변경은 워커 기회를 다시 만들지 않는다. 원문 근거, 승인, 미확정 쓰기, 취소와 사용자 정정 보호는 유지한다.

모델이 명시적으로 여러 완료 단계를 제안하는 `update_plan`은 기존의 제안 범위 검토를 유지한다. 모든 경우를 강제로 한 단계로 바꾸지 않는다. 자동 텍스트 fallback에서만 검토 범위를 분리했다. 단계를 각각 검토하므로 이 경로의 모델 호출이 추가될 수 있고, 속도 개선을 주장하지 않는다.

## 검증

- E-08 형태에서 첫 원문 확인만 통과하면1/3을 저장하고, 출처 시점과 최종 보고가 미확인이면 답변을 보류한다.
- 과거 완료 항목과 원래 완료 조건을 유지하며 진행 중 단계 우선 선택을 확인했다.
- 모든 단계 저장 뒤에도 최종 검토가 거부하면 답변은 전달하지 않는다.
- 검토 중 취소와 사용자 정정이 도착하면 이전 검토로 단계 저장을 진행하지 않는다.
- 기존 저장 실패, 미확정 쓰기, 승인, 명시적 다중 단계 제안 검사를 유지한다.

기본 관련28개 소스 검사, 문구 변경 복구 제한을 포함한 후속27개 검사, 제공자 계획 계약을 포함한 별도18개 검사, Office 공유 실행기 관련66개 검사가 통과했다. 일부 검사 파일이 중복되므로 합산 숫자를 전체 검사 수로 제시하지 않는다. Office 현재 실행 경로는 이번 브라우저 fallback 분기에 진입하지 않는다. 이 검사는 실제 Office COM 또는 실계정 모델 검증이 아니다.

[실제 Chrome 검사](../verification/sequential-plan/browser.json)는 합성 모델과 시험 사이트로1/3,2/3,3/3의 저장 및 화면 표시, 진행 중 새로고침, 최종 검토 전 답변 보류, 최종 답변 표시, 완료 뒤 새로고침을 확인했다. 페이지 읽기는1회, 단계 검토3회, 최종 검토1회다. 저장 완료와 React 표시 시점은 다르므로 최종 답변의 실제 표시를 별도로 기다려 검사한다.

[1/3 화면](../verification/sequential-plan/1-of-3.png), [3/3과 최종 답변](../verification/sequential-plan/final.png)을 직접 확인했다. 화면의 GLM 모델명은 합성 응답용 설정이며 실모델 GLM 품질 결과가 아니다.

초기 통합 검사는 기존 제공자, 질문 후 재개, 승인 시험의 일괄 완료/고정 호출 수 가정 때문에 각각 중단됐다. 각각 한 단계씩 저장된 상태를 엄격히 검사하도록 수정했으며, 실패 로그도 보존했다. 추가 호출은 실제 단계 완료를 동반해야 하고 쓰기1회 조건은 유지한다. 최종 후보 `468357661728ee33a989bdc63c44bb6b4567046ecc330d78925c2eced1c20d9f`의 [통합 검사](../verification/pre-release-2026-09-27T13-34-39-663Z/report.json)는20/20단계가 통과했다. 단위1,195개, 디자인/후보 빌드, 선택 Chrome7종17회다. 단계 진행, 사용자 입력, 하네스, 계획, 질문 재개의5종은 새 프로필에서 각각3회 통과했고 최종 누락 복구와 승인은 각각1회 통과했다. 전체 Chrome 행렬이나 실제 모델 품질 검사는 아니다. 배포하지 않았다. 기존 b4489e의 확인 통과5/10(50%)를 이 변경으로 올려 계산하지 않는다. PDF 읽기와 여러 카드의 값 혼동을 해결했다고 표시하지 않으며, 새 후보의 실제 E-08 완주 효과는 재측정이 필요하다.
