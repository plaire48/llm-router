# 채팅 종료 후 실행과 팝업 간섭 줄이기

상태: 2026-09-23 로컬 후보에 worker 실행 소유권과 진행 복원을 구현했다. 공개 배포와 회사망 실모델 검증은 별개다. 최종 검증 근거는 아래 구현 기록을 따른다.

## 결론

채팅을 닫아도 작업을 계속하는 것은 확장 내부에서 구현할 수 있다. Agent 실행을 채팅 문서에서 분리하고, 화면은 저장된 진행 상황을 구독한다. Chrome 종료나 확장 업데이트까지 실행이 유지된다는 의미는 아니다.

사이트가 만드는 모든 팝업의 OS 초점 이동까지 같은 Chrome 안에서 완전히 막는 것은 현재 구조와 공개 API만으로 보장할 수 없다. 작업 탭 분리, 불필요한 활성화 제거, 제한된 초점 복구는 개선할 수 있다. 실제 창을 표시하지 않는 별도 headless 브라우저는 더 강한 화면 격리를 제공하지만 로컬 실행기 또는 서버가 필요하고 기존 로그인 공유도 별도 문제다. 기본 제품에는 이를 필수로 추가하지 않는다.

## 변경 전 원인

- `src/App.jsx`의 `send()`가 `completeChat()`과 AbortController를 소유한다. Pi와 모델 스트림은 이 문서의 수명에 종속된다.
- `public/background.js`의 chat lease도 UI의 documentId/clientId에 묶인다. 화면이 사라지면 복구 경로는 진행 중 응답을 중단 상태로 바꾼다.
- `browser-workspace.js`는 비활성 작업 창을 만들고, 팝업이 만들어진 뒤 `guardPopupFocus()`로 이전 창의 초점을 복원한다. 사후 복구이므로 최초 초점 이동을 예방하지 못한다.
- 팝업 탭을 작업 창으로 옮길 때 생기는 추가 활성화, 지연된 팝업, 사용자가 직접 바꾼 창과의 경합을 따로 측정해야 한다. 새 창의 ID만 추적하는 현재 guard가 충분한지는 추가 실험 대상이다.

## 적용한 실행 구조

```text
채팅 화면 ── 시작 / 중지 / 질문 답변 / 승인 ──▶ 작업 관리자
          ◀──────── 진행 상황 구독 ─────────┘

작업 관리자 → Pi 실행 → 관찰 → 행동 → 검증
                    ↕ 단계별 체크포인트
               전용 작업 창과 소유 탭
```

1. service worker의 작업 관리자가 실행을 소유한다. 시작 요청은 작업 ID를 반환하고 끝나며, 화면의 연결 종료는 구독 해제만 한다. 현재 `RUN_TOOL` 직렬 대기열 안에서 전체 모델 루프를 기다리면 교착되므로 실행과 UI 명령 처리를 분리한다.
2. UI 문서 ID를 가장해 기존 RPC를 호출하지 않는다. worker 내부의 실행 권한과 UI 제어 권한을 분리하고 대화 ID, 제공자, 인증 시점, 실행 세대로 검사한다. 한 작업에는 하나의 실행자만 둔다.
3. 실행 단계, 순번, 계획, 도구 시작과 결과 영수증, 검증 상태를 저장한다. 채팅 재진입은 이를 읽을 뿐 같은 요청을 다시 시작하지 않는다. 토큰과 인증 자료는 기존 trusted session 경계를 유지한다.
4. worker가 강제 종료되면 저장된 체크포인트를 일시 중지 상태로 복구한다. 사용자 이어가기 때 현재 페이지부터 관찰한다. 중간에 결과가 끊긴 클릭이나 제출은 자동 재전송하지 않는다. 제출 성공 여부가 불명확하면 확인 또는 질문으로 전환한다. 브라우저 재시작 후 자동 업무 재개는 기존 정책대로 하지 않는다.
5. HITL과 질문은 `awaiting_user`로 저장하고 실행 자원을 정리한다. 창을 강제로 열지 않으며 확장 배지로 대기를 표시한다. 다시 연 채팅에서 기존 폼으로 답변하고 같은 작업을 이어간다. 중지는 UI가 다시 열려도 사용할 수 있어야 한다.
6. 제공자별 토큰 사용량, 완료 검토, 컨텍스트 압축, 이미지 비교, subagent 결과 수집을 실행자에 함께 이동한다. 결과가 이미 반영된 단계와 사용량은 다시 기록하지 않는다.

### worker 수명 검증

Chrome worker는 영구 프로세스가 아니다. 상태 저장 없이 `completeChat()`만 이동하면 다른 형태의 중단을 만든다. 이벤트별로 작업을 나누고, 수행 중인 장시간 작업에만 공식 문서의 제한적 수명 연장 패턴을 검토한다. 완료·취소·일반 질문 및 최종 승인 대기에는 해제한다. 과거 비자동화 입력 검토 모달은 기존 무활동 제한 안에서만 대기하며 화면 재진입으로 승인이 되지 않는다. 수명 유지만을 위해 디버거를 붙이지 않는다.

모델 응답 헤더 지연, 스트림 정지, 5분 이상 작업을 실제 Chrome에서 검사한다. worker에서 안정적으로 처리할 수 없는 경로가 확인되면 **전용 작업 창의 비활성 확장 실행 탭**을 대안으로 비교한다. 추가 설치 없이 기존 문서 기반 Pi/이미지 처리를 유지할 수 있지만 실행 탭이 남고, 그 탭의 종료·폐기까지 보호하지는 못한다. 이 대안을 보이지 않는 영구 프로세스로 설명하지 않는다.

Offscreen API는 SVG/Blob 이미지 비교 시트의 DOM 렌더링에만 BLOBS 사유로 사용하고 종료한다. Pi, 모델 호출, 브라우저 동작은 이 문서로 옮기지 않았다. 일반 Agent를 상시 실행하려고 `TESTING`이나 음성 재생 등 실제 용도와 다른 사유를 사용하지 않는다.

## 팝업 처리

- 누비가 직접 여는 탐색 탭은 명시적 windowId와 비활성 생성 옵션을 사용한다. 사용자의 창 열기 버튼만 의도적으로 작업 창을 앞으로 가져온다. Chrome이 `focused:false`를 무시하고 새 작업 창을 활성화하면, 원래 Chrome 창이 전경이었던 경우에만 정확히 그 새 창에서 한 번 복구한다.
- 사이트 클릭은 원래 이벤트와 팝업 계약을 유지한다. `window.open`을 일괄 덮어쓰거나 팝업 URL만 추출해 다시 열지 않는다. 이 방식은 POST, opener, 이름 있는 창, 초기 about:blank 작성과 SSO를 깨뜨릴 수 있다.
- 새 자식과 기존 이름 있는 창을 구분하고 작업에 속한 팝업만 추적한다. 팝업 발생부터 작업 창 편입까지의 초점 이벤트를 측정한다.
- 초점 복구는 한 동작의 제한된 기간에만 수행한다. 사용자가 다른 창이나 앱을 선택하면 오래된 창으로 되돌리는 반복을 하지 않는다. 전역 초점 고정 루프는 만들지 않는다.
- Chrome 창의 마지막 초점과 실제 OS 전경 앱을 구분한다. `getLastFocused()`만으로 사용자가 Chrome에 있다고 판단할 수 없다.

## 비교한 공식 자료와 오픈소스

- [Chrome worker 수명](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle): worker 종료와 영속 상태의 필요성. active debugger의 수명 연장은 실제 자동화 연결 중의 특성이며 로그인·대기 중 연결 유지의 근거로 사용하지 않는다.
- [장시간 작업 처리](https://developer.chrome.com/docs/extensions/develop/migrate/to-service-workers#keep_a_service_worker_alive): 수행 중인 예외적 장시간 작업에 한정한 수명 연장. 무기한 일반 keep-alive와 구분한다.
- [Offscreen 설계 의도](https://developer.chrome.com/blog/Offscreen-Documents-in-Manifest-v3): DOM 기능의 빈틈을 보완하는 API이며 범용 background page 대체로 취급하지 않는다.
- [Chrome windows API](https://developer.chrome.com/docs/extensions/reference/api/windows): 확장이 만드는 창의 `focused:false`와 사이트가 만든 창의 사후 이벤트는 다르다.
- [Nanobrowser background 구현](https://github.com/nanobrowser/nanobrowser/blob/master/chrome-extension/src/background/index.ts): Apache-2.0. executor를 background에 배치한 구조는 참고할 수 있다. 확인한 소스는 side panel의 `onDisconnect`에서 executor를 취소하므로 그대로 도입해도 이번 요구를 해결하지 않는다. 코드나 의존성을 추가하지 않았다.
- [Puppeteer headless 모드](https://pptr.dev/guides/headless-modes): 화면 없는 별도 브라우저 실행의 대안. 확장 설치만으로 별도 프로세스를 실행할 수 있다는 뜻은 아니다.

기존 Pi와 Playwright CRX를 유지하는 편이 타당하다. 이번 문제의 중심은 모델이나 계획 프레임워크보다 실행 소유권과 브라우저 창 수명이다.

## 구현 기록

- `background-runner.js`가 기존 Pi 루프, 모델 복구, 컨텍스트 압축, 역할별 분석, 사용량 기록을 실행한다. `START_AGENT`는 실행 ID를 곧바로 반환한다. 전체 루프를 RPC 직렬 대기열에서 기다리지 않는다.
- `public/background.js`의 내부 capability는 메시지로 전달할 수 없다. worker 소유 lease를 다른 채팅 UI가 `RUN_TOOL`이나 `FINISH_CHAT`로 가장할 수 없다. 동일 대화의 재진입 UI는 진행 조회, 명시적 중지와 기존 입력 검토 답변을 할 수 있다. 이전 UI 계약 `START_CHAT`의 문서 소유권은 호환 경로로 남지만 새 UI는 사용하지 않는다.
- 응답/단계는 trusted session, 계획/도구 영수증/최종 답변은 기존 대화 저장소에 남긴다. 도구 호출 전에 진행을 발행해 실행 중인 캡처가 원래 도구 단계에 표시된다. 화면의 저장소 조회는 실행을 재시작하지 않는다.
- `getPlatformInfo`의 제한된 호출은 실제 실행 중에만 유지된다. 이 목적으로 `chrome.debugger`를 연결하지 않는다. worker 소멸 시 실행을 자동 복제하지 않는다.
- 이미지 비교의 offscreen 문서는 렌더링 전용이다. 기존 질문/승인/CX 모달과 HTML 시각 토큰을 재사용하고 새로운 실행 화면은 만들지 않았다.
- 팝업은 실제 소유 opener로 초점 이벤트를 분류하고 작업 창으로 옮겨질 때의 초점도 복원 대상에 넣는다. 다른 앱이나 사용자가 선택한 다른 Chrome 창으로 이동하면 복원 시도를 멈춘다. 순간 OS 초점 이동의 완전 방지는 여전히 보장하지 않는다.

### 검증 방법

`background-lifetime-browser.mjs`는 Chrome을 직접 시작하고 UI 문서에만 CDP를 연결한다. worker에 inspector를 붙이거나 화면/스토리지 polling으로 수명을 연장하지 않는다. 채팅 UI를 모두 닫고 36초 헤더 지연과 모델 스트림을 실제 시간으로 기다린다. `NUBI_LONG_LIFETIME=1`은 315초 이상 실행을 확인한다. 새 화면에서 같은 결과/중지 권한을 검사하고 worker를 강제 종료한 뒤 자동 재실행이 없음을 확인한다.

`workspace-flow-browser`는 실제 도구가 대기 중일 때 보낸 UI를 닫고 다른 UI를 새로고침한다. 작업/검증이 계속되고 승인 전 등록 0회, 재진입 승인 후 1회를 검사한다. 컨텍스트/오류 복구 fixture는 기존의 화면 종료 취소 가정을 명시적 중지로 바꾸고, 응답 유실 주입 지점은 UI RPC에서 worker의 도구 경계로 이동했다. 검증 조건을 삭제하지 않았다.

실제 회사 계정, 실제 Qwen 정확도, Windows OS 초점 무간섭은 이 합성 모델 Chrome 검사에 포함하지 않는다. `verification/background-execution`과 이번 `verification/pre-release-*`의 보고서에서 통과 범위를 구분한다.

### 장시간 실행과 표시된 창 검증

- `verification/background-execution/lifetime-long.json`: 실제 시간 315초 모델 스트림, 첫 응답 헤더 36초 지연, 모든 채팅 화면 종료 상태에서 완료. worker debugger 연결과 UI 상태 polling 없이 검사했다. 재진입 후 응답은 한 번만 저장됐고, 명시적 중지와 강제 worker 종료 후 비재실행도 통과했다.
- `verification/background-execution/popup-headed-final.json`: macOS의 표시된 Chrome에서 작업 창 생성, 실제 입력/캡처, 새 탭과 새 팝업의 작업 창 편입 뒤 원래 사용자 창으로 초점 복구를 확인했다. 처음에는 새 작업 창 생성부터 초점을 빼앗는 실패가 있었고, 정확히 새 창만 한 번 복구한 뒤 통과했다.
- 이 검사는 동작이 끝난 시점의 초점 복구를 확인한다. 순간적인 OS 초점 이동, 다른 앱 사용 중 모든 경합, Windows 동작의 완전 격리를 증명하지 않는다.
