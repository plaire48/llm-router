# 브라우저 품질 재점검: beta34

2026-09-24. Chrome 확장의 이전 평가에서 빠진 대상 판별과 점수 집계를 점검했다. 임의의 종합 점수는 산출하지 않는다.

## 재현과 수정

| 문제 | 수정 전 반례 | 실제 반영 |
| --- | --- | --- |
| 다른 프레임/양식의 검증을 원래 입력과 혼동 | 같은 이름/역할의 필드가 다른 iframe URL, 소유 요소, 입력 ID, 양식 문맥에 있어도 대응 가능 | 실제 관찰의 frame 번호, URL, owner와 control ID/test ID/tag/type/context까지 대조 |
| 부분 화면에서 유일성 추정 | 필터된 결과나 잘린 제어 목록에서 같은 이름이 하나 보이면 새 ref 대응 가능 | DOM/제어 목록 범위가 완전하지 않으면 이름 기반 새 ref 대응을 거부. 본문 텍스트만 잘린 경우와 구분 |
| 평가 기록 누락 집계 | 계획 밖 실패 회차와 중복 계획을 무시해 성공 점수 산출 가능 | 계획/회차 무결성이 깨지면 점수와 반복 성공 지표를 미산정. 제외한 회차 수와 계획 오류를 명시 |

추가 회귀 3개가 기존 코드에서 실패하는 것을 확인한 후 수정했다. `before-regressions.log`와 `focused-after.log`에 남겼다. 새 라이브러리를 추가하지 않고 기존 Pi 실행기와 Playwright 검증을 보강했다.

## 방법론과 오픈소스 판단

[Playwright Locators](https://playwright.dev/docs/locators)와 [FrameLocator](https://playwright.dev/docs/api/class-framelocator)의 프레임 범위와 엄격한 대상 선택 원칙을 적용했다. 기존 Playwright/Playwright CRX와 dom-accessibility-api의 실제 관찰 메타데이터를 재사용했다. 이름이 맞는 첫 요소를 고르는 fallback은 추가하지 않았다. 정적 메타데이터 대응을 DOM 객체 동일성이나 서버 저장 증명으로 해석하지 않는다.

[Anthropic agent evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)의 과제/시도/실제 결과 분리 원칙을 점수 집계에 적용했다. 실패 회차를 유리하게 제외하지 않는다. WebArena-Verified 공식 채점기와 자체 과제 점수는 기존 분리를 유지한다. 현재 결함은 새 프레임워크 부재가 아니라 관찰 범위와 집계 무결성 문제여서 별도 실행기나 평가 프레임워크를 더 설치하지 않았다.

## 이번 검증

- 단위 검사: **612/612 통과**.
- 실제 Chrome: 영향 범위 5개 시나리오를 새 프로필로 3회씩 실행해 **15/15 통과**.
- 새 iframe 검사: 정상 content-script → Playwright 입력/검증 유지. 다른 URL의 같은 이름/값 필드는 호스트 값 검증이 통과하더라도 원래 작업의 결과로 인정하지 않음. 프레임 owner 교체와 필터 조회도 구분.
- 기존 검사: 입력 양식, 페이지 정보, 응답 유실 복구, 팝업 승인.
- 디자인 정적 검사와 candidate 빌드 통과. UI 소스는 변경하지 않았고 전체 시각 검토를 새로 했다고 주장하지 않는다.
- `npm audit --omit=dev`: 알려진 취약점 0개. 이 결과는 런타임 의존성 advisory 조회이며 코드 보안 감사나 무결점 보증이 아니다.

원본: `verification/pre-release-2026-09-24T08-01-10-392Z/report.json`.
요약: `verification/quality-beta34/SUMMARY.json`.

이전 54회 결과를 이번 실행 수에 합산하지 않았다. 이번 선택 범위 밖 회귀는 새로 확인한 것으로 표시하지 않는다. 검사한 후보는 보존했으며 공개 릴리스는 하지 않았다.

## 남은 한계

- 실제 Qwen 평가 인증은 현재 환경에 없다. 실제 업무 성공률과 공개 벤치마크 점수는 미측정이다.
- 공식 WebArena 실행 환경/초기화와 누비의 답변/HAR 자동 수집 어댑터는 여전히 필요하다. 공식 예제 채점 성공은 누비 성능이 아니다.
- 대상 문맥이 바뀌거나 부분 관찰이면 자동 해소가 보류될 수 있다. 모호한 대상에 완료를 부여하거나 미확정 쓰기를 재실행하지 않는다.
- 프레임 URL/소유 요소/필드 문맥이 같아도 동일 DOM 노드 또는 동일 업무 레코드임을 완전히 증명하지 않는다. 일반 스크립트와 외부 서버의 실제 저장은 업무별 결과 검증이 필요하다.
