# 완료 검토 실패 복구

## 확인한 문제

사용자가 본 `goal_review_failed` 문구는 완료 검토기의 형식/근거/문맥 오류에도 사용됐다. `src/api.js`에서 같은 검토 입력을 두 번 요청한 뒤 실패하면 `agent-runtime.js`의 최종 검토가 전체 실행을 종료했다. 실제 페이지 작업의 실패와 검토기의 장애가 충분히 분리되지 않았고, 일부 오류는 전달 중 세부 원인이 사라졌다. 아무 외부 근거도 없는 첫 답변의 의도 판별 실패도 같은 문구를 사용했다.

이는 소스와 고의 오류 주입으로 확인한 경로다. 사용자가 본 개별 실행의 제공자/모델/진단 기록은 확보하지 못했으므로 그 실행의 정확한 원인을 확정하지 않는다.

## 반영한 흐름

1. 같은 제공자/선택 모델로 기존 JSON 검토를 수행한다.
2. 형식/출력 오류는 결과 전용 스키마 도구로 다시 받는다. `report_goal_review`와 `report_completion_intent`는 보고 데이터이며 브라우저 도구로 실행하지 않는다. 정상 JSON 응답도 수용한다.
3. 모든 결과는 기존 엄격한 파서로 검증한다. 존재하지 않거나 오래된 근거 ID, 잘린 응답, 다른 도구/복수 도구 호출을 완료로 승격하지 않는다.
4. 최종 검토가 계속 실패하면 같은 실행의 읽기/검증 도구만 노출해 현재 결과를 다시 확인한다. 호스트 preflight에서도 입력/저장/스크립트/승인 요청을 차단한다. 이미 수행한 작업을 다시 실행하지 않는다.
5. 읽기 전용 복구 중 금지된 쓰기만 진전 없이 세 번 제안하면 호스트에서 실행을 차단한 채 질문 대기로 전환한다. 새로운 관찰 결과가 진전을 만든 경우에는 기존 no-progress 기록을 초기화한다.
6. 유효한 검토가 실제 누락을 지적하면 원래 도구 권한과 기존 승인 절차로 그 부분만 보완한다. 다시 형식 복구가 실패하면 기존 `ask_user`로 대기한다. 문맥 예산을 넘으면 원래 조건을 버리지 않고 분할 확인을 묻는다.
7. 외부 작업 여부 판별 자체가 실패하면 대상 페이지를 임의로 열지 않고 원하는 결과를 확인하는 질문으로 대기한다.

인증 실패와 명시적 취소는 위의 복구 대상이 아니다. 검토가 끝나지 않은 후보 답변은 계속 숨긴다. 질문 저장 실패는 성공 대기로 위장하지 않는다. 세부 `reviewReason`/`reviewPhase`를 보존하고 기존 작업 진단에 안전한 원인 코드만 남긴다. 최종 오류 문구는 **결과 검토 응답**을 확인하지 못한 상태로 명확히 했다.

## 검증

- 단위 오류 주입: 자유 JSON 실패 → 결과 스키마 수신, 잘못된 인용/다른 도구/복수 도구/출력 잘림 거부, 반복 실패/금지 동작 반복 시 질문 대기, 문맥 초과 시 원래 조건 유지, 취소/인증 비재시도.
- AI Pro와 ChatGPT Responses 전송을 합성 응답으로 검사했다. 같은 모델을 유지하고 결과 전용 도구가 실제 도구 실행기로 넘어가지 않음을 확인한다.
- 실제 Chrome `review-recovery-browser`: 다섯 필드를 작성/검증한 뒤 최종 검토 응답 두 번을 고의로 깨뜨린다. 새 읽기 전용 단계에서 모델이 중복 입력을 제안해도 실행되지 않으며, 새로운 관찰 후 유효한 검토로 마친다. 각 필드의 실제 input은 한 번, 등록은 0번이다. 원본 탭/초안/원래 제한을 유지한다.
- 첫 답변 판별 실패는 `completion-review-browser`에서 질문으로 대기하고 새로고침 뒤에도 질문/실행 상태가 유지되는지 검사한다.

Chrome은 실제 확장/DOM 실행이고 모델 응답과 사이트는 합성이다. 사용자의 실제 모델/업무 성공률 개선, 회사 SSO 및 외부 서비스 완료를 측정한 결과는 아니다. 원문 요구사항 자체가 모델 한도에 들어가지 않으면 자동 분할이 완료됐다고 주장하지 않고 사용자와 분할 범위를 확인한다. 공개 배포는 이번 작업 범위에 포함하지 않는다.

## 회귀 검사에서 보완한 항목

기존 `harness-browser`의 마지막 보호 검사는 페이지 이동만으로 쓰기 검증 부채가 생긴다고 가정했다. 현재 `requiresVerification`은 탐색과 실제 쓰기를 구분하므로 이 전제는 맞지 않았다. 검사를 실제 입력 한 건으로 바꾸고 DOM 값 변경과 `pending` 상태를 먼저 확인한 뒤, `FINISH_CHAT`의 미검증 완료 차단과 재개 후 검증 부채 유지까지 확인했다. 제품 완료 가드를 완화하지 않았다.

첫 답변 판별 재시도 검사는 기존의 “검토 도구 없음” 전제를 결과 전용 도구 계약으로 갱신했다. 형식 오류가 계속되면 페이지 입력 없이 질문으로 기다리고, 새로고침 후에도 질문과 대기가 유지되는지 확인했다.

검사 수정 중 실행 중이던 전체 gate 세 건은 해당 자식 프로세스만 의도적으로 중단했다. 그 실패 보고서는 통과 근거로 사용하지 않으며, 수정한 검사 입력의 해시로 전체 gate를 새로 실행한다.
