## 공식 근거와 최소 지원 후보

[PDF.js 공식 렌더링 예제](https://mozilla.github.io/pdf.js/examples/)는 getPage/getViewport/page.render로 개별 페이지를 canvas에 그리는 경로를 제공한다. [Anthropic PDF 지원 문서](https://platform.claude.com/docs/en/build-with-claude/pdf-support)는 페이지의 텍스트와 이미지를 함께 분석하는 방식을 설명한다. 이 방법론을 참고하되 Claude API나 다른 필수 서비스로 제공자를 바꾸지 않는다. 기존 pdfjs-dist와 offscreen 큐만 재사용한다.

1. 현재 소유 최상위 PDF의 문서 ID, 권한, 기존 원문 해시와 페이지 수를 확인한다. 모델이 명시한 **한 페이지**만 같은 바이트 스냅샷에서 렌더한다. 새로 가져오면 기대 원문 해시가 달라진 경우 거부한다. 임의 URL/새 권한/인증 PDF 지원을 추가하지 않는다.
2. [background-images.js:9](../background-images.js#L9)의 단일 offscreen 수명 큐와 Worker 정리를 재사용한다. 원본8MiB, 취소/기한을 유지하고 렌더 픽셀·이미지 바이트·동시 작업 한도를 검사한다. 원문을 보존해야 한다면 실행 내 한 스냅샷으로만 제한하고 종료/만료 때 해제하며 저장소에 남기지 않는다.
3. URL, rawHash, documentId, 실제 PDF 페이지 번호, 렌더 크기, 같은 페이지의 텍스트 범위와 **PDF 원문 참고 이미지** 표식을 함께 반환한다. screenshot_id, visualTargets, DOM ref를 만들지 않는다. 브라우저 캡처/현재 뷰포트/좌표 행동 권한으로 취급하지 않고 검토·하위 분석에도 이 출처 구분을 유지한다.
4. [model-routing.js:7](../model-routing.js#L7)의 인증된 현재 카탈로그 이미지 지원 경로만 사용한다. 지원 경로가 없으면 시각 미확인을 유지하고 필요한 예외를 접근 가능한 공식 텍스트에서 확인하거나 답변 범위를 제한한다. 자동 OCR, PDF 양식 편집, 전체 문서 이미지 열람을 구현한 것으로 표시하지 않는다.

본문에 관련 그림/범례 참조가 있거나 필요한 사실이 시각 정보에 의존할 때 해당 페이지를 후속 조회하는 방법이다. 모든 PDF나 선택한 조사 방법에 시각 검사를 새 필수 완료 조건으로 강제하지 않는다. 렌더 기능만 추가하거나 관련 없는 페이지 이미지를 보내는 것으로 예외 검증이 끝나지 않는다.

## 회귀 수용 기준

- 종목명을 쓰지 않은2쪽 로컬 PDF를 사용한다. 첫 쪽의 일반 규칙은 다음 쪽의 도형/색상/범례를 참조하고, 제외 영역은 그림에만 표현한다. 텍스트 읽기에는 시각 미검증이 남으며 지정한 쪽의 실제 PNG 색상·치수와 동일 원문 해시가 일치해야 한다.
- 같은 URL의 다른 바이트/문서 재로드, 범위 밖 페이지, 권한 철회, 이미지 한도, 렌더 실패·마감·취소와 이미지/PDF 큐 공존을 검사한다. 늦은 이미지가 전달되거나 작업이 자동 재개되면 실패다.
- 모델 wire와 최종 검토에 실제 PDF 페이지/해시/참고 이미지가 연결되어야 한다. PNG가 브라우저 최신 화면이나 클릭 좌표로 표기되면 실패다. 이미지가 없는데 예외나 시각 열람을 확인했다고 응답하는 합성 경로를 통과시키지 않는다.
- 로컬 렌더/합성 모델 통과와 실제 이미지 지원 모델의 예외 포함 정답·답변 전달·완료 계획을 분리한다. 실제 모델 개선 효과는 별도 고정 후보의 독립 채점으로 확인한다.


## 후속 구현

기존 `read_page`에 이미지 지원 모델이 있는 경우에만 `mode="pdf_page"`를 제공한다. 먼저 텍스트에서 관찰한 `pdf.raw_sha256`와 페이지 번호를 사용하며 한 페이지씩 읽는다. 반환 이미지는 `pdf_page_reference`로 분리하고 최신 브라우저 캡처, 클릭 좌표, 쓰기 증거로 등록하지 않는다. 주 실행기와 최종 검토에는 같은 원문 URL/해시/페이지의 이미지 최대2장만 전달한다. 현재 텍스트 전용 하위 분석 저장소에 픽셀을 읽은 것처럼 전달하지 않는다.

원문은 현재 작업의 한 PDF 캐시에만 유지한다. 문서/권한을 읽기 전후에 검사하고 해시가 달라지면 다시 텍스트를 확인하도록 한다. 렌더 출력4MP/PNG4MiB, 단일 offscreen 큐와 취소/마감을 적용한다. 미지원 모델, 범위 밖 페이지, 원문 변경, 늦게 도착한 이미지와 렌더 실패는 시각 근거로 전달하지 않는다. 실패해도 이미 읽은 텍스트까지 무효화하거나 같은 실패를 반복하도록 안내하지 않는다.

현재 읽을 수 있는 텍스트가 있는 공개 PDF만 지원한다. 인증 PDF, 스캔 전용 문서의 OCR, 양식 입력/편집, 모든 페이지의 자동 이미지 해석은 이번 범위가 아니다. 텍스트와 이미지 결합은 [Anthropic PDF 지원](https://platform.claude.com/docs/en/build-with-claude/pdf-support)의 방법을 참고하고, 실제 렌더는 기존 Apache-2.0 [PDF.js](https://mozilla.github.io/pdf.js/examples/)를 재사용한다. API 제공자나 추가 라이브러리는 도입하지 않았다.


이미지2장 제한은 **모델 요청과 최종 검토에 첨부하는 상한**이다. Pi 원본 실행 기록의 이전 이미지 파트는 누적될 수 있으므로 전체 실행 메모리2장 상한으로 표시하지 않는다. 현재 text-only 하위 워커는 PDF 그림을 읽지 않는다. 대량 페이지의 이미지 메모리 회수와 하위 워커 직접 시각 분석은 후속 최적화 경계다.

## 렌더 구현 검증

`src/pdf-text.js`의 `renderPdfPage`와 `browser-document-worker.js`가 기존 PDF.js worker 및 보조 canvas의 크기를 제한한다. `browser-pdf-parser.js`는 전송한 바이트 스냅샷과 job nonce를 묶고 렌더 Worker를30초 후 종료한다. `background-images.js`의 `renderCurrentPdfPage`는 기존 첨부/비교/텍스트 추출과 같은 직렬 offscreen 큐를 사용하며35초 기한과 취소 때 문서를 정리한다. 원문8MiB, 페이지 수2000, 지정 페이지1개, 출력 긴 변2000px/4MP/PNG4MiB로 제한한다. PDF.js 보조 canvas도 개별4MP, 합계12MP로 제한하며 출력 canvas와 분리한다. 렌더러는 텍스트를 재추출하지 않아 긴 본문 때문에 정상 그림을 거부하지 않는다. 텍스트/페이지 범위는 호스트의 같은 원문 캐시를 사용한다.

- `tests/pdf-render.test.mjs`의8개 회귀는 페이지/픽셀/PNG 제한, PDF.js 안전 옵션, Worker nonce와30초 마감, 문서/Worker 정리, 기존 큐 공유, 대기/실행 중 취소 및 늦은 이미지 거부를 검증한다. 기존 PDF/호스트 검사와 함께23/23 통과했다.
- `tests/browser-pdf-render-browser.mjs`는 임시 확장에서 실제 `runBrowserAgent`를 호출했다.2쪽 로컬 PDF의 파란 영역과 흰 제외 영역을 PNG 픽셀로 확인하고, 같은 원문 해시/문서 ID/페이지와 비조작 이미지 분리, 이미지 미지원/다른 해시/범위 밖 페이지 거부, 긴 본문/기존 이미지 큐 공존, 실패 뒤 offscreen0개를 확인했다.4개 검사 통과. [기록](../verification/browser-pdf/render-browser.json).
- 같은 공식 FIE 원문을 별도 disposable Chrome renderer로 읽었다. 원문 SHA-256 `852d636402dccb7bbd107c346261430a1b1977ab0fe9c2a2ae663af52b5bd880`,61쪽 중34쪽. PNG893×1263px/191,658bytes, 렌더 호출 왕복521ms, 종료 후 offscreen0개. Figure6, 파란 유효면/흰 손과 다리, 그림은 안내용이며 적절한 규정 본문이 우선한다는 원문 표시를 직접 확인했다. [원문 렌더 기록](../verification/browser-pdf/public-fie-render.json), [실제 PNG](../verification/browser-pdf/public-fie-page34.png).

이 검사는 source overlay와 공개 PDF의 렌더 기능을 확인한다. 실제 배포 후보의 통합검사와 실계정 이미지 모델이 예외를 정확히 설명하고 작업을 완료하는 검증은 별도로 수행한다. 이미지 렌더 성공을 규칙 해석 정답으로 판정하지 않는다. PNG에서 보이는 그림의 본문 우선 경고도 함께 읽어야 한다.


첫 통합 검사에서는 PDF 안내가 일반 문서 검토에도 추가되어 기존 10,000토큰 비교 검사의 문맥 한도를 넘었다. [실패 기록](../verification/pre-release-2026-09-27T20-18-52-877Z/report.json). PDF 근거가 있을 때만 관련 지침을 추가하도록 수정했으며 기존 예산과 양쪽 원문 보존 조건을 유지했다. 관련 65개 검사 통과 후 전체 통합 검사를 다시 실행한다.


디자인 검사에서 문서 렌더의 명시적인 흰색 배경이 UI 색상 규칙에 걸려, PDF.js의 동일한 기본 종이 배경을 사용하도록 중복 지정을 제거했다. 배경색을 누비 브랜드색으로 바꾸거나 디자인 검사를 우회하지 않았다. 고정 라이브러리의 `RenderParameters.background` 기본값을 확인했고 실제 PNG 흰색 제외 영역 회귀를 유지한다.


## 최종 통합 결과

후보 SHA-256 `9bdfe924091e1c2fb3bcbba9db2e6fe255f4cc7edff9e2a910ab350bd0093fe6`를 고정해 **단위 1,299개, 디자인 검사, 후보 빌드, 실제 Chrome 회귀 44종**을 통과했다. [통합 기록](../verification/pre-release-2026-09-27T20-22-29-352Z/report.json). 새 PDF 렌더 회귀는 source overlay 없이 실제 dist를 사용했고 파란 영역과 흰 제외 영역의 픽셀, 해시, 문서 연결을 확인했다. 원래 PDF 텍스트 읽기, 이미지 모델 연결, 계획/최종 검토, 디버그 표시, 입력/승인, Wiki와 대화 회귀도 포함한다.

이는 로컬 구현과 합성 모델/사이트의 회귀 통과다. 실제 모델의 예외 포함 정답률과 과제 완주율은 아직 미측정이다. 사용자 요청에 따라 실모델 재시험을 보류하고 품질 개선을 먼저 반영했다. 첫 후보의 20% 점수와 새 후보의 검사 통과를 합산하지 않는다. 남은 기능 경계는 스캔 OCR/인증 PDF/양식 편집, PDF 이미지의 하위 워커 직접 분석, Pi 원본 이미지 메모리 회수다.
