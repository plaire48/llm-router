# 누비의 정적 사이트 제작과 배포

상태: 2026-09-21 타당성 검토와 구현 제안. 0.16.9에 포함된 기능이 아니다. 로컬 실행기 설치 여부와 대상 업로드 서비스는 아직 정하지 않았다.

## 목표

사용자가 보고 있는 페이지를 참고해 프로젝트를 만들고, 선택한 폴더에 저장한다. 누비가 의존성 설치, 빌드, 로컬 미리보기, 사용자 피드백 반영과 테스트를 수행한다. 완성된 빌드 결과를 대상 서비스가 받는 형식으로 준비하고, 사용자 승인 뒤 업로드와 실제 배포 결과까지 확인한다.

개발에는 Node/npm을 사용할 수 있다. 첫 배포 결과는 정적 HTML/CSS/JS와 이미지이며 실행 시 Node 서버가 필요한 SSR, 자체 API와 데이터베이스는 제외한다. React/Vite를 첫 검증 대상으로 삼고 Vue/Vite, Astro 정적 출력 등은 실행 계약을 공유하도록 설계한다.

외부 페이지에서 얻는 것은 DOM, 스타일, 이미지와 관찰 가능한 동작이다. 이것으로 유사한 페이지를 새로 구현할 수 있지만 비공개 원본 컴포넌트나 서버 기능을 복원했다고 주장하지 않는다. 실제로 관찰한 화면과 확보한 자산을 참고 자료로 기록한다.

## 현재 확인한 구현

- `agent-runtime.js`의 Pi agent core가 기존 제공자 호출과 도구 실행 루프를 소유한다.
- `agent-harness.js`는 브라우저 도구 선택과 동작 뒤 새 검증을 요구한다.
- `browser-agent.js`의 생성 코드 실행 경로는 제한된 Playwright facade다. PC 파일, Node 프로세스, shell, `setInputFiles`는 노출하지 않으며 파일 입력란도 차단한다.
- `public/manifest.json`에는 `nativeMessaging`이 없다. 현재 CSP는 OpenWiki 읽기 연결용 loopback HTTP를 허용하지만, 코드 작성/설치/빌드 작업 API와 실행기는 아직 없다. 네트워크 접근 허용과 로컬 명령 실행 기능을 구분한다.
- 코드 하이라이팅과 브라우저 JS 실행은 로컬 프로젝트 실행 능력을 의미하지 않는다. 파일 저장, npm 실행, 개발 서버, 프로젝트 결과물 업로드는 신규 구현이 필요하다.

기존 [OpenWiki 연결 설계](./OPENWIKI-LOCAL-DEVELOPMENT.md)의 선택적 로컬 프로젝트 연결과 역할을 공유한다. OpenWiki는 큰 기존 프로젝트의 코드 이해를 보조하며 신규 정적 프로젝트 생성의 필수 선행 작업으로 두지 않는다.

## 실행 환경 선택

| 방식 | 가능한 일 | 제약 | 권고 |
| --- | --- | --- | --- |
| 확장과 브라우저 파일 API | 사용자가 고른 폴더 읽기/쓰기, 코드/결과물 다운로드 | 경로 문자열만으로 접근 불가. PC npm/명령어/localhost 프로세스 실행 불가 | 파일 내보내기에 사용 가능 |
| 확장과 WebContainer 작업 페이지 | 브라우저 안 Node/npm, 가상 파일 시스템, 미리보기 | PC shell과 별개. native addon 미지원, COOP/COEP와 MV3 분리 검토, 사내 네트워크와 상용 라이선스 확인 필요 | 설치 없는 JS 프로젝트용 별도 후보 |
| 확장과 선택적 로컬 실행기 | 실제 폴더, Node/npm, 빌드, localhost, 파일 테스트 | 최초 실행기 설치 필요. Windows/macOS 배포와 프로세스 관리 필요 | 사용자가 설명한 전체 흐름에 가장 적합 |

기존 채팅과 페이지 자동화는 계속 확장만으로 작동한다. 로컬 실행기는 프로젝트 제작 기능을 선택할 때만 연결한다. 기존 llm-router를 다시 필수로 만들거나 별도 LLM 인증을 요구하지 않는다.

로컬 연결은 Chrome Native Messaging을 우선 제안한다. 설치 프로그램이 실행기와 host manifest를 등록해야 하며 확장 ZIP만으로 설치되지는 않는다. 확장 ID를 정확히 허용하고 worker에서 요청 소유권을 검사한다. 제어용 공개 localhost HTTP 서버 없이 시작할 수 있다. 개발 미리보기 서버만 loopback 주소로 연다.

설치 없는 대안은 별도 HTTPS 작업 페이지의 WebContainer다. 그 미리보기 URL을 PC에서 실행 중인 localhost 서버라고 표시하지 않는다. npm으로 받은 프로젝트 코드를 확장 권한이 있는 페이지에서 직접 실행하지 않는다. 브라우저 파일 선택 권한과 가상 프로젝트의 동기화는 별도 구현이다.

## 사용자 흐름

1. **참고 페이지 관찰**: 현재 페이지와 사용자 요청에서 화면, 필요한 기능과 완료 조건을 정한다. 미확인 기능은 질문하거나 범위를 표시한다.
2. **폴더 선택**: 첫 작업에서만 폴더 선택을 요청한다. 주소 입력도 실행기의 실제 경로 확인과 사용자가 선택한 작업 범위에 연결한다. 기존 폴더면 현재 변경을 보존하고 분리된 작업 복사본을 만든다.
3. **작성과 실행**: 여러 소스 파일과 package.json을 만들고 의존성을 설치한다. 개발 서버가 준비되면 새 탭으로 미리보기를 연다.
4. **대화로 수정**: 사용자가 미리보기를 보며 “메뉴를 좁혀줘”처럼 요청한다. 누비가 수정하고 새 화면 및 관련 동작을 다시 확인한다.
5. **최종 빌드 검증**: 배포용 결과물을 별도로 빌드하고 그 결과물로 미리보기한다. 개발 서버 성공만으로 완료하지 않는다.
6. **대상에 맞춰 업로드**: 목적 서비스의 규격을 확인하고 업로드 자료와 실제 공개 범위를 보여준다. 승인 후 전송하고 배포 주소를 열어 재검증한다.

별도 스튜디오 메뉴를 만들지 않는다. 채팅에는 프로젝트 이름과 현재 단계만 표시하고 미리보기, 폴더, 변경 파일, 다운로드는 아이콘과 툴팁으로 제공한다. 로그와 파일 diff는 필요할 때 펼친다. 중지 버튼은 실행 중에만 보인다. 상세 경로, 포트와 명령 전체를 상시 표시하지 않는다.

## 실행과 검증 구조

```mermaid
flowchart LR
  U[사용자 요청과 참고 페이지] --> A[누비의 기존 Pi 하네스]
  A --> F[파일 작성과 의존성 설치]
  F --> B[빌드와 미리보기]
  B --> V[DOM과 화면 및 동작 검증]
  V -->|오류 또는 수정 요청| A
  V --> D[최종 결과물 준비]
  D --> H[업로드 승인]
  H --> P[대상 서비스에 업로드]
  P --> Q[배포 주소에서 재검증]
```

로컬 실행기는 모델을 다시 호출하는 별도 Agent가 아니다. 기존 모델과 Pi 루프가 필요한 도구를 선택하고 실행기는 구조화된 결과를 돌려준다. 여러 Agent가 같은 프로젝트를 동시에 수정하는 구조로 시작하지 않는다.

추가할 도구 계약의 예:

| 도구 | 입력과 결과 |
| --- | --- |
| `project_open` | 사용자 선택에 연결된 projectId, 실제 작업 위치와 현재 revision |
| `project_read` / `project_patch` | 프로젝트 상대 경로, 기대 파일 해시, 변경 결과와 새 revision |
| `project_install` | 패키지명/버전/목적, lockfile 변경, jobId와 설치 결과 |
| `project_run` | 프로젝트의 dev/build/test 작업, jobId, 종료 코드와 제한된 로그 |
| `project_job` | jobId의 상태 조회, 로그 이어 읽기, 취소와 실제 종료 확인 |
| `project_preview` | buildId 또는 개발 revision에 묶인 URL과 서버 상태 |
| `project_artifact` | 검증한 buildId, 상대 경로 목록, 크기와 파일 해시 |
| `upload_artifact` | artifactId와 대상 탭/문서/입력란, 승인 ID, 전송 결과 |

프로젝트 쓰기도 검증 의무를 만든다. 기존 `verify_page`만으로 파일, 설치, 빌드와 배포를 모두 검증한 것으로 취급하지 않는다. 코드 revision → buildId → preview 검증 → artifact hash → 업로드 결과를 이어 기록한다. 중간에 코드나 배포 경로가 바뀌면 이후 검증과 승인을 무효화한다.

긴 빌드는 jobId로 조회한다. 패널을 닫아도 보조 실행기의 작업 상태를 복구할 수 있게 하고, 재접속 시 설치나 업로드를 무조건 다시 실행하지 않는다. Native Messaging 연결 수명만 믿지 말고 작업을 소유하는 프로세스와 저널의 종료/재접속 계약을 구현한다. 비밀 환경변수와 인증값은 모델 로그에 담지 않는다.

명령 실패는 exit code와 오류 위치를 바탕으로 수정한다. 실행 제한을 임의 단계 수로 두지 않고 사용자 중지, 실제 오류, 진행 없는 반복과 작업 자원 제한을 구별한다. 이미 성공한 외부 쓰기는 재시도하지 않고 상태부터 확인한다.

## 의존성 설치

사용자가 맡긴 프로젝트 범위에서 필요한 패키지를 설치하고 잠금 파일에 버전을 남긴다. 기존 lockfile 재현은 `npm ci`, 새 의존성 추가는 프로젝트 단위 설치를 사용하며 전역 설치를 기본으로 하지 않는다. 사내 registry, proxy, CA 설정을 사용할 수 있어야 한다. 네트워크나 인증 실패를 코드 오류처럼 재시도하지 않는다.

Node/npm 실행은 임의 프로젝트 코드와 설치 스크립트를 실행할 수 있다. `cwd` 제한이나 허용 명령 이름만으로 PC 파일 접근을 격리했다고 주장하지 않는다. 호스트에 필요한 최소 환경만 전달하고 프로젝트 작업 복사본을 사용한다. 자동 설치/실행을 안전하게 확대하려면 OS별 격리 범위와 허용한 스크립트를 별도로 검증한다. 격리가 없는 개발 시제품은 그 한계를 명시한다.

## 대상 페이지에 맞는 업로드

대상 URL을 먼저 관찰해 ZIP, 다중 파일, 폴더, 저장소 push 중 무엇을 받는지 확인한다. 기존 업로더 규격이나 공식 API가 있으면 이를 어댑터로 사용하고 브라우저 UI 방식은 허용된 파일 입력 도구로 지원한다. 알 수 없는 규격을 추측해 전송하지 않는다.

단순히 HTML 하나를 올리지 않고 최종 출력 폴더의 JS/CSS/이미지를 포함한다. 배포 base path, 하위 경로 새로고침, SPA fallback 지원, 크기/확장자 제한, 원격 자산 의존성을 확인한다. SPA fallback이 없으면 hash routing이나 정적 다중 페이지 등 대상에 맞는 결과물을 만든다. `node_modules`, 원본 비밀 파일과 로컬 개발 설정은 결과물에 넣지 않는다.

기존 Playwright facade의 파일 입력 차단을 통째로 해제하지 않는다. 검증한 artifactId로만 파일 바이트/파일을 공급하는 `upload_artifact`를 추가한다. 일반 Playwright의 파일 업로드 지원과 현재 playwright-crx에서 실제 가능한 전송 방식은 구별하여 검증한다. 큰 결과물은 Native Messaging의 단일 메시지 한도에 맞춘 청크, 순서와 해시 검사가 필요하다.

파일 선택 즉시 서버로 전송하는 페이지도 있으므로 최종 제출 버튼만 승인 지점으로 삼지 않는다. 최초 외부 전송 전에 대상, 파일 수/크기, 공개/교체 범위와 artifact hash를 승인에 묶는다. 사용자가 승인 카드에서 수정을 요청하면 수정, 재빌드와 새 검증 후 다시 준비한다.

업로드 요청 200, 파일 목록 등록, 공개 배포 성공을 별도로 기록한다. 공개 URL에서 index와 관련 자산을 읽고 실제 화면, 링크와 새로고침을 확인한 뒤에만 배포 완료로 표시한다.

## 첫 검증 범위

첫 PoC는 React/Vite 프로젝트 하나와 검증 가능한 업로드 대상 하나로 고정한다. 인증 제공자는 기존 AI Pro/ChatGPT/FabriX 어댑터를 그대로 사용한다. 설치와 빌드가 도구로 성공하는 것과 실제 LLM이 필요한 도구를 골라 전체 작업을 완료하는 것은 별도 증거다.

| 시나리오 | 성공 기준 |
| --- | --- |
| 참고 페이지 → 새 프로젝트 | 지정 폴더에 여러 소스 파일이 생기고 화면 구조/핵심 동작이 요구사항과 일치 |
| 필요한 라이브러리 추가 | 실제 설치 완료, lockfile 반영, 관련 기능 브라우저 확인 |
| 의도적인 빌드 오류 | 오류를 읽고 해당 파일 수정 후 실제 빌드 성공 |
| 미리보기에서 사용자 수정 | 새 revision과 화면 일치, 관련 기능 재검증 |
| 포트 충돌/실행 중 패널 닫힘 | 실제 준비된 URL로 연결, 재접속 시 같은 job 확인, 중복 실행 없음 |
| 다른 작업의 파일 수정 | 해시 충돌을 인식하고 사용자 변경을 덮어쓰지 않음 |
| 배포용 결과 검증 | 개발 서버와 별개로 최종 출력에서 콘솔 오류, 자산 404, 반응형, 핵심 조작과 새로고침 확인 |
| ZIP/다중 파일 업로드 | 대상 규격과 경로에 맞는 결과물, 승인 전 외부 전송 없음 |
| 중간 실패/응답 유실 | 실제 등록 상태 확인 후 재개, 중복 업로드 없음 |
| 실제 서비스 최종 확인 | 배포 URL에서 화면과 자산/라우팅 성공, 로컬 fixture 검증과 분리 |

첫 구현 순서는 파일/작업 실행 계약 → 빌드/미리보기/수정 반복 → 결과물 전송과 승인 → 대상 서비스 실검증이다. 전체 흐름 검증 전 이 설계를 설치 가능한 확장 기능으로 표시하지 않는다.

## 확인한 공식 자료

- [Chrome Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging): 별도 프로그램 등록, 확장과 프로세스 연결, 메시지 크기와 수명.
- [File System Access](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access): 사용자 선택과 권한을 통한 파일/폴더 읽기와 저장.
- [WebContainer 시작 예제](https://webcontainers.io/guides/quickstart), [브라우저 요구사항](https://webcontainers.io/guides/browser-support), [native addon 제약](https://webcontainers.io/guides/troubleshooting), [상용 사용 안내](https://webcontainers.io/enterprise): 가상 npm/미리보기 대안과 적용 전 확인할 조건.
- [Chrome 원격 코드 안내](https://developer.chrome.com/docs/extensions/develop/migrate/remote-hosted-code): 확장 권한 영역과 동적 프로젝트 실행 영역을 분리해야 하는 배포 검토 근거.
- [Vite 정적 배포](https://vite.dev/guide/static-deploy), [빌드 base 경로](https://vite.dev/guide/build): 최종 출력물, 로컬 검증과 대상 경로.
- [Playwright 파일 업로드](https://playwright.dev/docs/input#upload-files): 기본 도구의 파일/메모리 업로드 계약. 누비의 CRX 전송 구현 성공을 뜻하지 않는다.

이번 검토는 현재 소스와 공식 문서를 대조했다. 새 로컬 실행기, WebContainer 연결, 실제 npm 자동 복구와 서비스 업로드 PoC는 아직 실행하지 않았다.
