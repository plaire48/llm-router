# CX 디자인 개발 규칙

CX UI 스킬은 `skills/cx-ui`에서 배포합니다. `node scripts/install-skill.mjs`로 설치할 도구와 프로젝트를 선택하고 Codex에서는 `$cx-ui`, Claude Code에서는 `/cx-ui`로 호출합니다. 도구별 설치·요청 예제는 `docs/SKILLS.md`에 있습니다. 새 프로젝트 생성 시 --skill-target codex|claude|all을 명시한 경우에만 선택한 도구에 설치됩니다. 설치한 스킬은 현재 프로젝트의 패키지 버전을 조회해 아래 기준과 예제를 사용합니다.

이 프로젝트는 @e2e/cx-design-system의 밝은 테마와 컴포넌트를 사용합니다. 2026-09-21 사용자가 제공한 HTML을 지속적인 시각 표준으로 지정했으므로, 모든 기존/신규 요소의 색상, 서체/크기/굵기/행간, 간격, 버튼/아이콘 비율, 반경, 그림자, 애니메이션은 [시각 기준](docs/VISUAL-STANDARD.md)과 공유 서비스 토큰 `design/agent-deck.css`를 우선합니다. 로그인부터 모든 모달과 상태 화면까지 같은 기준을 적용하며, 제공자나 화면마다 별도 시각 체계를 만들지 않습니다. 작업 전 package.json에서 설치 버전을 확인합니다. 사람과 에이전트 모두 같은 기준을 사용합니다.

1. 먼저 `agent/library.json`에서 템플릿과 조합 규칙을 고르고 `tokens/catalog.json`에서 관련 토큰을 확인합니다. `docs/TEMPLATES.txt`의 명령으로 새 프로젝트 또는 빈 화면 폴더에 복사합니다. 기존 셸 안에서는 `embedded`를 전달하고 화면의 `app.css`도 연결합니다. 복사본의 API·라우팅·저장 책임은 서비스에 있습니다. 이어서 `node_modules/@e2e/cx-design-system/agent/manifest.json`에서 필요한 컴포넌트·패턴을 찾습니다. 세부 디자인은 `agent/design-index.json`의 분류·기본 규격·원본 경로로 찾고 필요한 `reference/design-details.json` 선언만 확인합니다. 해당 패키지의 docs/IDENTITY.md, docs/COMPONENTS.md와 관련 docs/PATTERNS.md를 읽습니다.
2. 앱 진입점에서 `@e2e/cx-design-system/styles.css`를 한 번 불러옵니다. 전역 프레임은 CxAppShell을 사용합니다.
3. manifest의 portable API를 먼저 사용합니다. reference-only 항목은 제품 의존성을 분리해야 하는 참고 소스입니다. 이름이 있다는 이유로 import 경로를 추측하지 않습니다.
4. 색상·서체·간격·모서리·그림자는 공통 CSS 변수를 사용합니다. 임의 색상, 외부 웹폰트, 화면별 공통 컴포넌트 덮어쓰기를 추가하지 않습니다. 새 배치는 별도 클래스와 토큰으로 작성합니다.
버튼·입력은 기본 32px, 작은 조작 토큰은 28px이며 주 입력 장치가 터치인 (pointer: coarse)일 때 44px로 전환합니다. 공통 CSS가 처리하므로 별도 고정 높이와 존재하지 않는 size prop을 추가하지 않습니다.

5. 추가·수정·닫기 등은 ActionButton의 action 사전을 사용합니다. 익숙한 아이콘과 배치만으로 의미가 명확한 조작은 저장과 취소도 아이콘만 표시합니다. 사용자 지시에 따라 이 원칙은 CX의 기본 텍스트 버튼보다 우선합니다. 버튼에는 접근 가능한 이름과 호버/키보드 포커스 툴팁을 제공합니다. 제공자/모델 이름, 모호한 작업, 삭제 확인과 오류 복구에 필요한 문구는 짧게 유지합니다. 같은 상태를 색상/테두리와 텍스트로 불필요하게 반복하지 않습니다.
6. 입력 label, 오류와 안내 연결, 키보드 이동, 모달 초점 복귀를 유지합니다. 저장 실패 때 초안을 지우지 않습니다. 미저장 이동과 닫기를 같은 정책으로 구현합니다.
7. 기본·로딩·빈 결과·오류·읽기·수정·저장 실패 등 해당되는 상태를 구현합니다. 짧은 한국어 문구와 실제 동작을 일치시킵니다.
   한 주제에는 핵심 문장을 먼저 두고 필요한 상세만 덧붙입니다. 핵심 구절과 짧은 소제목은 600 굵기, 설명은 본문 크기를 유지한 보조색으로 구분합니다. 강조색은 중요한 의미에만 쓰며 색만으로 정보를 구분하지 않습니다. 이미지와 아이콘은 이해를 돕거나 텍스트를 명확하게 대체할 때 사용합니다.
8. npm run verify:identity로 디자인 검사, 후보 빌드와 실제 Chrome 화면 검사를 실행합니다. 정적 검사 통과만으로 디자인 적합성을 선언하지 않습니다. 작은 화면과 마지막 콘텐츠·푸터를 포함합니다.
9. 공통 기능이 없으면 기존 조합을 먼저 검토합니다. 새로운 공통 요소가 필요하면 사용 목적·상태·API·토큰·예제·검증을 갖춰 디자인 시스템 변경으로 제안합니다. 제품 요구사항과 디자인 시스템을 함께 기록합니다.

명시적 사용자 요구가 이 기본 기준과 충돌하면 사용자 요구를 따르되 바뀐 디자인 결정과 영향 범위를 기록합니다. 새 프로젝트의 네트워크·저장·인증은 서비스가 구현하며 디자인 예제의 메모리 동작을 실제 저장으로 표현하지 않습니다.

가독성과 의미 전달을 최우선으로 합니다. 한 주제는 핵심 문장 → 판단에 필요한 조건/대상/결과 순서로 구성하고 제목을 반복하는 설명은 제거합니다. 강조는 문단 전체가 아니라 핵심 구절에 600 굵기와 진한 의미 색상을 함께 사용합니다. 보조 설명도 본문 크기를 유지합니다. 이미지/아이콘으로 같은 의미가 더 명확하게 전달되면 우선 사용하되, 승인 조건과 입력 이름처럼 해석이 필요한 글자는 남깁니다. 상세 기준은 VISUAL-STANDARD.md의 ‘문장과 강조의 우선순위’를 따릅니다.

토스트와 로딩은 `agent/feedback-contract.json`과 `docs/FEEDBACK.md`를 따른다. 왼쪽 원은 3초 표시 시간이며 작업 진행률이 아니다. 오류와 재시도도 자동으로 닫히므로 지속적 복구 경로는 화면에 남긴다. API·진단 복사·교체·수명·모달·키보드·모션 감소를 함께 확인한다.
