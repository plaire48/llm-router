# 작업 중단과 오류 복구

누비 Desktop의 복구 순서는 **원래 요청 보존 → 실제 결과 확인 → 원인 분석 → 미완료 부분 수정안 → 실행 결과 재검토**입니다. 모델 연결 재시도와 명령 재실행을 구분합니다. 복구했다고 완료 조건을 통과시키지 않습니다.

## 실제 적용한 동작

| 상황 | 처리 | 이어가는 기준 |
|---|---|---|
| 일시적인 네트워크·408/429/5xx, 모델 응답 중단 | 기존 누비의 `recoverModel`과 p-retry로 추론 호출만 최대 3회 시도. 이미 받은 도구 결과는 유지 | 성공한 응답으로 같은 Pi 실행을 계속함. 인증/취소/잘못된 요청은 자동 재시도하지 않음 |
| 모델 문맥 한도 초과 | 기존 공통 context manager로 한 번 압축 후 해당 추론 재호출 | 원래 요청·모든 AC·답변을 보존. 다시 실패하면 기록을 유지하고 복구 대기 |
| 소스·Wiki·관계 조회가 반환되지 않음 | 읽기 도구에 30초 제한, 오류를 모델에 반환 | 모델이 범위·경로·조회 방식을 수정. 늦은 읽기 결과로 수정 권한을 추가하지 않음 |
| 제안/계획 등 로컬 기록 도구가 반환되지 않음 | 60초 후 결과 미확정으로 기록, 해당 Agent 중지 | 실제 원래 호출이 끝나기 전에는 새 실행·명령·프로젝트/작업공간 전환 차단. 같은 쓰기를 재전송하지 않음 |
| Bash 문법 오류·없는 셸 | 실행 기록을 먼저 저장하고 Bash `-n` 사전 검사 | 문법 오류가 있는 명령의 정상 접두부도 실행하지 않음. 앱 종료/취소 뒤 검사 결과가 와도 명령을 시작하지 않음 |
| 명령의 비정상 종료·설정한 시간 초과 | 연결된 모델이 실제 profile/script/종료 코드/출력/현재 파일을 조회하고 자동 원인 분석 | 코드 변경안 또는 정확한 수정 명령을 제안. 기존 코드 반영·명령 실행 HITL 유지 |
| 사용자가 수정 명령 실행 | 제안 ID를 먼저 예약하여 동시 클릭·응답 유실·새로고침에 중복 실행 방지 | 원래 시간 제한을 유지. 실제 결과를 다시 모델이 검토하며 전체 AC는 별도 검증 |
| 앱/호스트 강제 종료 후 재열기 | 작업·도구·프로세스를 `interrupted`로 구분하고 기록 복구 | **이어서 진행**에서 파일 해시·제안·실행 기록을 다시 조회. 이전 명령 자동 실행 없음 |
| 저장은 끝났지만 적용 응답 유실 | 실제 파일 해시가 제안 결과와 일치하면 반영 기록만 복구 | 파일을 다시 쓰지 않음. 다른 내용이면 기존 충돌 처리 유지 |
| 사용자 취소·대기 중 질문 | 취소 상태·질문 및 초안 유지 | 취소된 작업 자동 재개 금지. 질문은 같은 작업의 기존 응답 흐름으로 이어감 |

`실행과 비교 → 실행 복구 설정`에서 실패 시 AI 분석과 명령 시간 제한을 설정합니다. 기본 시간 제한 0은 로컬 개발 서버를 위한 계속 실행이며 출력이 없다고 서버를 죽이지 않습니다. stdin은 닫힌 비대화형 실행입니다. 대화형 셸은 기존 Theia 터미널을 사용합니다.

모델의 기본 무응답 제한은 120초이며 실제 스트림 활동으로 갱신합니다. 지수 백오프와 jitter를 사용하고, 같은 실행의 하위 분석도 제공자의 Retry-After를 공유합니다. 60초보다 긴 제공자 대기 지시는 조기 재호출하지 않고 복구 대기로 남깁니다. 시간/연결 재시도 제한은 추론 복구의 범위이며 전체 업무 완료 기준이 아닙니다. 도구가 반복 실패하면 공통 Pi의 결과 비교·재계획·질문 경로를 사용합니다.

## 방법론과 오픈소스 판단

- [Anthropic의 장기 실행 하네스](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents): 작업 상태를 명시적으로 기록하고 다음 실행에서 실제 환경을 다시 확인하는 방법을 적용했습니다. 원래 완료 조건·이전 답변·소스 해시·도구 시작/종료 기록을 SQLite에 남깁니다. 자동 Git 커밋/리셋은 도입하지 않았습니다.
- [Codex App Server](https://developers.openai.com/codex/app-server/): thread/turn/item 수명, 시작/완료 이벤트, 중단 기록과 재개를 구분하는 설계를 참고했습니다. 기존 Theia/Pi 실행기에 맞춰 기록과 재조회 방식을 적용했으며 Codex 런타임을 번들하거나 Codex 인증을 공유하지 않습니다.
- **실제 재사용:** 기존 Nubi Pi 0.86.1 실행기, `model-recovery.js`, context manager, 분석 coordinator와 SQLite 작업 저장소를 사용합니다. [p-retry 8.0.1](https://github.com/sindresorhus/p-retry) 및 is-network-error 1.3.2를 정확한 버전으로 직접 선언했습니다. 두 패키지는 MIT입니다. 새 모델 서비스나 외부 복구 서버 비용은 없지만 재시도·진단·결과 검토의 모델 사용량은 발생합니다.
- **검토 후 미도입:** [LangGraph checkpointing](https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint/README.md)의 지속 기록 패턴을 참고했습니다. 현재 이미 Pi와 SQLite에 실행 소유권·HITL이 있어 전체 LangGraph 런타임을 추가하면 두 실행 상태와 승인 계약을 관리해야 합니다. 이번 범위에서는 효과가 입증되지 않아 추가하지 않았습니다.
- **CX:** 공통 DeckDisclosure/CxNotice/CxButton을 재사용합니다. 자동 닫힘 토스트에만 복구 행동을 두지 않고, 실패 기록·명령 제안·이어가기 동작을 화면에 유지합니다. 사용자가 준 HTML의 글꼴·크기·모션을 유지합니다.

복구 도구 기록은 기존 **Wiki에 기록**에 포함됩니다. 명령 원문·터미널 출력·인증값을 Git Markdown에 넣지 않고 도구 종류·상태·고정 오류 코드·미확정 여부만 내보냅니다. 로컬 실행 로그는 기존 전용 상태 디렉터리에 보관합니다. Wiki 저장은 자동 commit이나 자동 전체 Wiki 갱신이 아닙니다.

## 검증과 한계

2026-09-25 개선: 모델은 `read_process_output`으로 저장된 실행 로그를 구간별로 읽거나 문자 그대로 검색할 수 있습니다. 복구 문맥에는 보존 버퍼의 앞뒤 미리보기와 원문 조회 ID를 남깁니다. 연속 조회는 revision으로 변경을 확인하고 로그를 다시 얻기 위해 명령을 재실행하지 않습니다. 조회한 근거는 읽기 전용 복구 워커에 전달할 수 있습니다. [공개 소스 비교와 적용 범위](AGENT-BENCHMARK-2026-09-25.md)를 따릅니다.

`tests/recovery.test.mjs`는 실제 Pi에 합성 모델을 연결해 네트워크 중단, 무응답, 문맥 초과, 읽기 멈춤, 미확정 기록 도구, 취소와 재개를 주입합니다. 실제 Bash의 문법 오류·없는 명령·시간 초과·수정 명령 실행, 동시 요청 중복 방지, SQLite 재열기 및 실제 파일 readback도 검사합니다. 실제 Theia에서는 오류 표시→명령 검토/실행→출력 확인→새로고침→중복 없음과 좁은 화면을 검증합니다. 상세 결과는 [검증 기록](VERIFICATION.md)을 참조합니다.

- 운영체제/Node 이벤트 루프 자체의 정지나 강제 종료를 프로세스 내부 타이머로 복구할 수는 없습니다. 외부 supervisor를 추가한 것은 아닙니다. 재시작 후 미확정 상태 확인 경로를 제공합니다.
- 읽기 제한은 모델 대기와 늦은 결과 채택을 막습니다. 모든 OS I/O를 강제 취소한다는 뜻은 아닙니다. 미완료 기록 작업은 결과가 확정되기 전까지 격리합니다.
- 호스트 강제 종료는 이미 시작한 자식 프로세스의 종료를 증명하지 않습니다. PID가 재사용될 수 있어 과거 PID를 무조건 종료하거나 명령을 재전송하지 않습니다.
- Bash 사전 파싱만 구현했습니다. PowerShell 문법 사전 검사, 실제 Windows Git Bash/PowerShell 및 사내 모델의 오류 진단 정확도는 아직 검증하지 않았습니다.
- 재시작 뒤 과거 명령을 자동 분석/실행하는 스케줄러는 없습니다. 같은 살아 있는 호스트에서 새로 끝난 실패 명령만 자동 진단 대기열에 넣습니다. 인증은 메모리에만 있으므로 호스트 재시작 시 다시 연결해야 합니다.
- 모델의 진단·수정안은 오답일 수 있습니다. 코드 반영과 수정 명령 실행은 기존 사용자 동작을 유지하고, 실제 실행 기록을 완료 조건의 성공으로 바꾸지 않습니다.
