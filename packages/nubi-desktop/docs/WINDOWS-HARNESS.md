# Windows 앱 작업 하네스

2026-09-23. 기존 Pi, 문맥 관리자와 분석 담당 조정기를 Windows UIA 및 캡처 근거에 연결했다. 하네스 계약 테스트의 native 응답은 주입한 합성 데이터다. 별도 Windows workflow의 WPF 검증은 실모델 정확도나 회사 앱 호환 검증과 구분한다.

## 사용자 흐름

1. 작업을 만들고 실행할 앱을 등록하거나 열린 창을 연결한다.
2. 누비가 UIA 정보와 필요한 캡처를 읽는다. 이미지 입력이 없는 모델은 `includeImage:false`를 사용한다.
3. 복잡한 화면, 결과 검토나 실패 원인 분석은 기존 `page`, `review`, `recovery` 하위 분석에 필요한 근거 ID만 전달한다.
4. 주 실행기가 현재 관찰을 바탕으로 한 동작을 제안한다. 제안이 만들어지면 Pi 실행은 승인 대기로 돌아간다.
5. 사용자 승인 뒤 호스트가 한 번 실행하고 실제 값과 화면을 확인한다.
6. `결과 분석하고 이어가기`는 저장된 동작 결과를 같은 작업의 새 분석에 연결한다. 다음 동작은 다시 제안하고 승인받는다.

앱 실행 결과에서 분석을 시작하려면 먼저 대상 창을 연결해야 한다. 분석 버튼은 네이티브 동작을 다시 호출하지 않는다. 연결 실패나 분석 중단도 원래 동작 영수증을 변경하지 않는다. 사용자 취소, 대기 질문, 미확정 동작은 이 경로로 우회하지 못한다.

## 근거와 문맥

`observe_computer`의 UIA 요소와 PNG는 현재 실행의 공용 근거 저장소에 들어간다. 기존 조정기가 최대 두 분석 담당의 실행, 지정 근거 ID, 제한된 문맥, 부분 결과와 취소를 관리한다. 새로운 멀티 에이전트 프레임워크를 추가하지 않았다.

하위 분석은 `read_analysis_evidence`로 지정된 동결 근거를 읽는다. 화면 분석과 검토에는 같은 제공자의 이미지 경로를 사용한다. 주 대화와 다른 작업은 전달하지 않는다. 하위 분석에 native 관찰, 앱 시작, 마우스, 입력, 승인 도구를 제공하지 않는다. 기존 문서 조사 담당의 소스/Wiki 읽기 범위도 그대로다.

동결 근거는 이미지가 있어도 현재 조작 권한이 아니다. 새 관찰 뒤 이전 UIA 근거는 stale이며, 저장된 동작 결과는 항상 historical이다. 주 실행기는 새 동작 전 현재 실행에서 직접 관찰해야 한다. 예전 이미지에 보이는 좌표를 클릭 권한으로 변환하지 않는다. 실제 Windows 상태는 실행 직전에 기존 어댑터가 다시 검사한다.

기존 문맥 관리를 적용한다.

- UIA 전체를 계속 붙이지 않고 근거 ID와 `read_analysis_evidence`의 검색/구간 조회로 필요한 정보만 읽는다.
- 원본이 실행 저장소에 남아 있는 오래된 UIA 텍스트만 참조로 치환한다. 최신 두 읽기, 이미지, 오류와 실행 영수증은 이 치환에서 보호한다.
- 원래 요구사항과 사용자 답변, 시작 시점의 미확정 동작은 모델 요약과 별개로 문맥 압축 후에도 유지한다.
- `computer_checkpoint`는 최신 동작 8개, 대조 4개와 미해결 개수/생략 개수를 제공한다. 경로, 입력값, 창 제목과 PNG를 반복 전송하지 않는다.
- `read_computer_result`는 ID로 이전 동작 상태와 선택한 전/후 캡처를 읽는다. 모델의 이미지 재조회에는 그 캡처를 만든 원래 창 연결이 필요하다. 연결 해제/재시작 뒤에는 다시 연결한 창을 새로 관찰한다.

문맥 요약과 하위 분석 보고서는 조언이다. 실행 확인, 저장 완료, 업무 성공 또는 사용자 승인으로 취급하지 않는다. 실제 확인 사실은 호스트 영수증과 개별 값 대조 결과로 남긴다.

## 복구와 사용자 확인

Windows 오류가 같은 화면에서 반복되면 도구 결과를 모델에 돌려 다음 관찰이나 대상 선택을 바꾸게 한다. 새 관찰 ID나 이미지 속 커서/애니메이션만으로 실패 기록을 초기화하지 않는다. UIA 내용이 바뀌거나 새로운 정확한 값 대조가 성공했을 때 진전으로 본다.

세 번 진전 없이 실패하면 동일 작업에 기존 `QuestionForm` 질문을 만들고 답변을 기다린다. 질문은 실행 승인이 아니다. 미확정 클릭이나 앱 시작은 자동 재전송하지 않는다. 분석 연결 오류는 앱 동작 성공/실패와 별도로 표시한다. 재시작 시 진행 중이던 결과 분석은 interrupted로 바뀌며 자동 재개하지 않는다.

## 검증

계약 검사는 실제 Pi 모델 호출 경로에 합성 응답을 주입한다. Windows PNG가 두 분석 담당에게 전달되는지, 부모 대화와 native 권한이 격리되는지, 과거 관찰로 클릭 제안을 할 수 없는지 확인한다. 문맥 압축 뒤 미확정 영수증과 원래 완료 조건이 보존되는지, 반복 실패가 질문으로 전환되는지도 검사한다.

UI 검사는 결과 분석 버튼, 중복 실행 방지, 좁은 레이아웃과 기존 로그인/작업 화면을 확인한다. 실제 Windows 11, DPI/다중 모니터, 사내 앱, 실모델의 화면 해석과 최종 업무 품질은 [COMPUTER-USE.md](COMPUTER-USE.md)의 Windows 검증 범위에 남아 있다.


## 공통 창 관찰 개선 (2026-09-23)

- `observe_computer({query:"검색",includeImage:false})`는 Microsoft winapp의 실제 UIA `search`를 연결된 HWND 안에서 호출한다. 기존 깊이 5/150개 조회에 없는 컨트롤을 최대 20개까지 찾는다. 검색은 입력을 실행하지 않는다. `coverage`와 `truncated`로 부분 조회임을 보존하며, 결과가 없다고 커스텀 화면에도 대상이 없다고 판단하지 않는다.
- 공식 검색 명령의 `exit 1 + 빈 matches`만 정상적인 빈 결과로 처리한다. 액션 실패, 타임아웃, 중단과 오류 JSON에는 적용하지 않는다. 중복 selector와 잘못된 개수는 거부한다.
- 클릭과 invoke 후 기존 요소가 사라져도 연결된 창 전체를 캡처하고 새 UIA 트리를 저장한다. 호버도 창 전체, 값 입력은 기존 요소 캡처와 정확한 값 대조를 유지한다. 창 정체성이 달라졌거나 관찰이 실패하면 미확정 상태를 유지한다.
- `read_computer_result`는 새 화면의 historical UIA도 반환하므로 이미지 없는 모델도 결과 구조를 검토할 수 있다. UIA와 이미지는 순차 조회이므로 동시에 고정된 상태라고 주장하지 않는다. 저장된 근거에는 원래 창 연결이 필요하며 다음 행동 전 새 관찰이 필요하다.
- 검색어 변경, 새 근거 ID, 요소 순서 변경은 진전으로 취급하지 않는다. 동일 범위의 UIA가 실제로 달라져야 반복 실패 횟수를 초기화한다. 비교 캐시는 16개 범위로 제한한다.

구현 계약은 [winapp search 소스](https://github.com/microsoft/winappCli/blob/main/src/winapp-CLI/WinApp.Cli/Commands/UiSearchCommand.cs)와 공식 UIA 문서를 확인했다. [UFO의 AppAgent](https://github.com/microsoft/UFO/blob/main/documents/docs/ufo2/app_agent/overview.md)의 구조 관찰과 화면 관찰 조합을 기존 Pi에 적용했다. UFO 전체나 별도 하위 에이전트 런타임을 추가한 것은 아니다.

회귀 시나리오는 첫 150개 밖의 검색 대상, 검색 0건과 오류 구분, 클릭한 요소가 사라진 새 화면, 연결 해제 후 근거 접근 차단, 쿼리/순서 변경을 통한 무한 재시도 방지다. 실제 Windows에서 앱을 움직인 결과는 별도 검증 대상이다.

## UIA 상태와 Wiki 근거

선택, 체크 설정, 펼치기와 접기를 기존 승인 흐름으로 실행하고 실제 상태를 다시 조회한다. 주 실행기가 현재 조회한 OpenWiki-SDS 근거를 동작에 연결하며 문맥 압축 이후 다시 조회한다. 제안과 실행 직전에 근거 변경을 검사한다. 상세 선택과 검증은 [개선 기록](../../../docs/research/2026-09-23-nubi-local-windows-uia.md)을 따른다.
