# 프로젝트 규칙과 새 파일 생성

2026-09-23. 기존 파일 수정만 가능했던 코딩 흐름에 새 파일 제안을 추가했습니다. 프로젝트가 Git으로 관리하는 개발 규칙을 실행 문맥과 변경 계획에 연결했습니다. 별도 모델, 서버, 패키지 의존성은 추가하지 않았습니다.

## 검토와 선택

| 근거 | 반영한 내용 | 도입 경계 |
|---|---|---|
| [OpenCode rules](https://opencode.ai/docs/rules/), 기존에 고정해 검토한 instruction.ts | 프로젝트의 AGENTS.md를 우선 읽고 없으면 같은 디렉터리의 CLAUDE.md 사용. 필요한 경로의 규칙만 조회 | 방법론 적용. 홈 설정, 외부 URL, OpenCode 인증/실행기는 가져오지 않음 |
| [OpenCode write 도구 실제 소스](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/tool/write.ts) | 새 파일도 변경 비교와 진단 피드백에 포함 | 현재 공식 소스의 permission → write → diagnostics 흐름을 확인. 누비는 디스크 반영 전 검사하고 사용자가 반영. LSP 전체나 자동 포맷터는 미도입 |
| [Anthropic 장기 실행 하네스](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) | 계획, 실제 변경, 검증 결과를 구분하고 다음 실행에 관찰 가능한 기록 전달 | 기존 SQLite 작업 기록과 Pi 문맥 관리 재사용. 파일 해시 일치를 테스트 통과로 올리지 않음 |
| 기존 Pi, Theia/Monaco, diff, TypeScript/JSONC/YAML | 도구 실행, 문맥, 네이티브 diff, 변경 줄 수, 실제 파서 재사용 | 실행기 교체와 상태 체계 중복 도입 불필요. 추가 패키지 없음 |

OpenCode write의 비교 대상은 2026-09-23 조회한 dev 소스입니다. 파일 생성, diff, edit 권한 확인, LSP 진단 반환을 확인했으며 소스를 제품에 복사하지 않았습니다. 이전 고정 커밋과 라이선스 검토는 [코드 변경 품질](CODING-AGENT-QUALITY.md)을 따릅니다. OpenCode/Pi/diff는 MIT, TypeScript는 Apache-2.0, YAML은 ISC이며 현재 패키지 라이선스를 유지합니다. 성능 순위를 근거로 실행기를 교체한 것은 아닙니다.

## 사용 흐름

1. 작업 시작 시 프로젝트 루트 규칙을 읽습니다. 소스 조회 또는 새 경로 확인 시 해당 파일의 부모 경로 규칙을 순서대로 읽습니다. 하위 디렉터리 규칙이 상위의 같은 항목보다 우선합니다.
2. 새 파일은 `inspect_path`로 현재 파일이 없는지 확인합니다. 이 관찰은 현재 실행에만 유효합니다. 기존 파일 조회를 생성 관찰로 대체하지 않습니다.
3. 원래 완료 조건과 새 파일을 `record_change_plan`의 `action: create`로 연결합니다. OpenWiki 근거와 실제 코드 관찰 계약을 유지합니다. 그래프 연결이 없는 새 파일의 영향은 미확인입니다.
4. `propose_new_file`은 파서 검사 후 검토 자료만 저장합니다. 기존 변경 제안 카드에 **새 파일**, 검사 결과, 비교와 반영을 표시합니다.
5. 반영 시 다시 경로와 규칙, 문법을 검사합니다. 열린 동일 URI의 미저장 편집을 보호하고, 호스트가 `wx`로 기존 파일을 덮어쓰지 않는 생성만 수행합니다. 실제 파일 해시를 다시 읽어 성공을 기록합니다.
6. Wiki 기록은 승인 전 파일을 생성 대기로, 반영 후 파일을 현재 내용과 대조해 표시합니다. 문법 검사, 파일 저장, 기능 검증 상태는 별개입니다.

## 변경과 복구

규칙 파일 해시뿐 아니라 없었던 규칙의 경로도 fingerprint에 포함합니다. 새 규칙이 추가되거나 CLAUDE.md보다 우선하는 AGENTS.md가 생기면 계획과 승인 대기 제안이 무효화됩니다. AI가 규칙을 다시 읽고 계획을 갱신해야 합니다. 같은 소스 해시와 수정 내용이어도 규칙이 다르면 과거 제안을 재사용하지 않습니다.

같은 이름의 파일이 생기면 내용이 같아도 생성 성공으로 처리하지 않습니다. 이미 반영된 제안만 실제 내용 대조 후 재호출을 허용합니다. 생성 중 호스트가 종료되거나 readback이 불확실하면 확인 필요 상태를 보존하고 자동 생성 재시도를 하지 않습니다. 실제 파일을 읽어 새 변경 계획을 세워야 합니다. 사용자 취소와 진행 중 질문은 새 파일 반영을 막습니다.

규칙은 코딩 문맥이며 실행 권한이 아닙니다. 시스템/사용자 지시와 호스트의 승인 및 경로 검증을 바꾸지 않습니다. 홈 규칙, 외부 링크, 참조 문서를 자동으로 가져오지 않습니다. 루트부터 대상 디렉터리까지 최대 20단계, 규칙 파일당 32 KiB, 총 64 KiB입니다. 초과 또는 읽기 실패를 숨기거나 성공으로 잘라 전달하지 않습니다. 루트 규칙은 기존 문맥 관리의 유지 항목에 포함하고, 경로별 규칙은 소스 도구 응답에 포함합니다. 문맥 압축 후에는 이전 소스/생성 관찰을 비우므로, 수정 전에 해당 코드와 최신 규칙을 다시 읽어야 합니다.

## 남은 범위

- 새 텍스트 파일만 지원합니다. 부모 폴더가 없으면 기존 환경 준비 제안과 사용자 승인으로 폴더를 먼저 만듭니다. 바이너리/이미지 생성, 자동 폴더 생성, 파일 삭제/이동, 여러 파일의 원자적 일괄 반영은 제공하지 않습니다.
- 경로 이탈, 심볼릭 링크 부모, 기존 파일과 Windows 예약 파일명을 거부합니다. 애플리케이션 검사와 배타적 파일 생성이며 OS 샌드박스나 외부 프로세스와의 원자적 디렉터리 잠금은 아닙니다.
- AGENTS.override.md, 사용자 전역 규칙, opencode.json의 glob/원격 규칙, 임의 hook 실행은 미지원입니다. 다른 도구의 전체 규칙 계약과 동일하다고 표시하지 않습니다.
- 전체 LSP/타입 검사, 실제 모델의 수정 성공률, Windows 실행은 별도 검증이 필요합니다. 이미지에서 요구사항과 소스를 찾는 기능, 데이터 의미/컬럼 계보 확대는 기존 조사 단계입니다.
- 다음 개선은 동일한 고정 과제에서 사내 모델의 요구사항 충족률과 변경 실패율을 먼저 측정하고, 실제 실패 사례에 필요한 LSP 또는 구조 검색을 선택하는 순서가 적합합니다. 라이브러리 수를 품질 지표로 삼지 않습니다.

## 검증

`tests/project-rules-new-files.test.mjs`에서 실제 Git 파일, 파서, SQLite와 Pi 합성 응답을 사용합니다. 경로별 규칙 우선순위와 fallback, 외부 링크/크기 제한, 새 규칙으로 인한 무효화, 현재 실행의 생성 관찰과 계획, 잘못된 문법, 동일 내용의 파일 충돌, 생성 중단, readback과 재열기, Wiki 생성 대기 상태를 확인합니다.

`scripts/check-ui.mjs`는 실제 Theia와 Chrome에서 기존 편집 보호와 함께 새 파일 비교/반영, 실제 파일, 화면 재열기, 충돌과 규칙 변경 차단, 좁은 레이아웃을 확인합니다. 최신 통과 수와 로그는 [검증 기록](VERIFICATION.md)에 남깁니다. 합성 모델 도구 연결은 실모델 품질 측정이 아닙니다.
