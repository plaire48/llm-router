# 폼 명확성 점검

2026-09-25. 사용자는 필요한 선택과 입력만 하고, 누비가 근거에서 결정할 수 있는 기술 설정은 먼저 준비한다. 짧은 질문, 선택지, 하단 직접 답변을 기본으로 유지한다. 폼 답변과 실제 실행 승인은 다른 계약이다.

## 화면별 검토

| 폼 | 입력 부담과 판단 | 반영 |
| --- | --- | --- |
| 요청과 후속 대화 | 자유 입력 하나. 별도 완료 조건 작성이나 작업 모드 선택은 불필요 | 기존 단일 입력 유지. 질문 대기 중 중복 입력란 숨김 유지 |
| 확인 질문 | 질문과 선택지, 직접 답변이 같은 카드에 있어 맥락 유지 가능 | 공유 QuestionForm 재사용. 한 질문과 필요한 설명 유지 |
| 앱 선택 | 창을 찾는 단계와 연결 단계의 질문이 같고, 목록에서 파일 선택으로 돌아가기 어려움 | 목록에서는 “어느 창에 연결할까요?”. “다른 방법으로 선택”으로 돌아가며 작성 중 답변 유지 |
| DB 연결 | 8개 입력 항목과 암호화 선택을 한꺼번에 요구. MySQL/Oracle 스키마를 중복 입력 | 기본 5개 제어만 표시. 연결 ID, 포트, 변경 가능한 스키마와 TLS는 연결 옵션에 배치 |
| 모델 선택과 로그인 | 서비스별 계정 연결과 모델 검색이 필요. 인증은 사용자 제공 영역 | 기존 공통 Nubi 컴포넌트 유지. 임의 계정/모델 선택이나 인증 생략 없음 |
| FabriX | Endpoint, Client Key, API Token 세 가지가 실제 계약에 필요 | 기존 테스트 후 연결과 비밀 입력 유지. 임의 추정으로 필수 값을 없애지 않음 |
| 스킬 등록 | ZIP/폴더 선택으로 하위 파일까지 가져옴. 별도 등록 명세 작성 불필요 | 기존 파일 선택 유지 |
| VOC 가져오기 | 파일 선택과 검색이 핵심. JSON 작성 폼을 새로 노출할 필요 없음 | 기존 파일 선택과 출처 확인 유지 |
| 소스/Wiki/관계 탐색 | 검색과 관계 중심 선택의 구분이 필요 | 관계 선택에 보이는 “확인할 항목” 라벨 추가 |
| 직접 실행/화면 비교 | 명령, 셸, 주소는 고급 수동 조작에 필요 | 보조 모달 유지. 일반 요청에서 입력을 요구하지 않음 |
| 실행/관리자/마우스 승인 | 대상, 명령, 예상 변경과 권한을 보고 판단해야 함 | 핵심 정보와 명시적 승인 이름 유지. 간결함을 위해 승인 대상을 숨기지 않음 |

## 변경 전후

- DB: 종류, ID, 주소, 포트, DB, 스키마, 사용자, 비밀번호 → 종류, 주소, DB, 사용자, 비밀번호. 포트와 ID 등은 “연결 옵션”에서 변경한다. 실제 접속 정보가 모두 자동으로 알아지는 것으로 표현하지 않는다.
- MySQL/MariaDB: DB 이름과 같은 값을 스키마에도 입력 → 현재 DB 이름에서 유도한다. Oracle은 현재 로그인 사용자 대문자 이름을 기존 호스트 계약에 맞춰 사용한다. PostgreSQL `public`, SQL Server `dbo`는 옵션에서 변경할 수 있다.
- 옵션을 접어도 사용자가 변경한 포트/스키마/ID를 유지한다. 접힌 필드가 잘못되면 해당 영역을 펼쳐 수정하게 한다. 연결 중 입력을 잠그고 실패하면 값을 유지하며 성공 후 비밀번호를 비운다.
- 앱: 목록에서도 “어떤 앱을 확인할까요?” → “어느 창에 연결할까요?”. 이전 방법으로 돌아가도 답변 초안을 보존하며 앱 연결/입력 RPC는 호출하지 않는다.
- 관계 선택: 접근성 이름만 있는 선택창 → 보이는 라벨도 제공한다.

## 방법론과 오픈소스 판단

- [Codex 공개 질문 스키마](https://github.com/openai/codex/blob/aa380897f67b91e1a47d530d7286d497b6726d3f/codex-rs/core/src/tools/handlers/request_user_input_spec.rs), Apache-2.0: 한 질문을 우선하고 짧은 선택지와 자유 입력을 구분한다. 질문 ID와 답변 연결, 적은 선택 수를 참고했다. 전체 TUI나 실행기를 가져오지 않았다.
- [OpenCode 질문 스키마](https://github.com/anomalyco/opencode/blob/16c56fe5ecc3305028d1f0a9cff5806e51c9d480/packages/schema/src/v1/question.ts), MIT: 완전한 질문, 짧은 선택 이름과 설명, custom 답변 계약을 확인했다. [공식 question 설명](https://opencode.ai/docs/tools/#question)과 함께 기존 QuestionForm 유지의 근거로 사용했다. Effect/Solid 기반 질문 런타임을 React 앱에 추가하지 않았다.
- [Anthropic 사용자 입력 가이드](https://code.claude.com/docs/en/agent-sdk/user-input): 명확화 질문과 도구 승인을 구분하고 선택 답변 또는 실제 자유 입력을 원래 질문에 연결한다. 문서화된 계약을 참고했으며 비공개 Claude Desktop 구현을 분석했다고 주장하지 않는다.
- [W3C 폼 안내](https://www.w3.org/WAI/tutorials/forms/instructions/): 보이는 라벨과 필요한 입력 안내, 수정 가능한 오류를 확인했다. placeholder만으로 필드 이름을 대신하지 않는다.
- 실제 구현은 설치된 React와 CX의 Input/Select/Button/Notice, 공통 Nubi QuestionForm, 표준 HTML details/label/required를 재사용한다. 현재 필드 수와 계약에는 새로운 폼 상태 라이브러리가 불필요하다. 코드 복제나 새로운 npm 의존성은 없다.

`cognitive-accessibility:simplify` 스킬에 따라 판단 부담, 기억해야 할 값, 현재 해야 할 행동을 점검했다. 단순 외형 평가이며 실제 사용자 관찰 실험이나 정량 사용성 점수는 아니다.

## 검증 범위

DB UI는 합성 어댑터로 5개 엔진의 실제 전달 인수, 기본 TLS, 실패 후 입력 유지, 성공 후 비밀번호 삭제, 접힌 옵션 보존과 잘못된 필드의 펼침을 확인한다. 실제 회사 DB 로그인 성공을 의미하지 않는다. 앱 폼은 초안을 유지한 뒤 돌아가기에서 연결 RPC가 발생하지 않는지 확인한다. 기존 Theia/공유 화면 검사는 로그인, 스킬, 질문 재진입, 승인과 키보드/좁은 화면을 포함한다. Windows 11, 회사 SSO, 실제 사용자 사용성 검증은 별도다.

최종 검사: Theia 49개, 스킬 등록 12개, 공유 UI 37개, DB 폼 7개로 화면 105개가 통과했다. DB/앱 연결 런타임 21개, 기준 HTML 디자인 검사와 브라우저 개발 빌드도 통과했다. DB 폼 입력 전달은 합성 어댑터이며 실제 DB 접속은 수행하지 않았다. 증적과 전후 화면은 `verification/form-clarity/`에 있다.

## 재점검: 실패 후 다음 행동

같은 폼을 다시 검토할 때 이미 해결한 배치를 반복 변경하지 않았다. 요청/질문, 앱 선택, DB 연결, 제공자 연결, 스킬 등록, VOC, 수동 실행/비교와 승인 흐름의 입력/전송/오류 상태를 다시 확인했다. 이번에는 결과 안내가 실제 실패 단계와 맞지 않는 세 부분을 수정했다.

| 이전 | 개선 | 확인할 동작 |
| --- | --- | --- |
| 앱 창 조회 실패가 공통 “답변 전송 실패”로 표시됨 | 창 조회, 대상 변경, Windows 실행기 연결 등 현재 오류에 맞는 안내 | 창 조회 실패 시 앱을 확인하고 다시 찾도록 안내. 답변/조작 성공으로 표시하지 않음 |
| DB 연결 성공 후 목록 조회 실패가 연결 오류로 섞임 | 실제 작업 응답의 연결 정보를 유지하고 목록 오류를 별도로 표시 | “연결 상태 다시 확인”은 상태 조회만 호출. 재연결/스키마 재수집 호출 없음 |
| VOC 저장 성공 후 검색 실패가 가져오기 실패처럼 보임 | 보관 완료 안내와 목록 읽기 실패를 구분 | 검색으로 목록만 다시 조회. 파일을 다시 가져오지 않음 |

DB 초기 상태 요청이 늦게 돌아와 새 작업 결과를 덮지 않도록 조회 순서를 검사한다. VOC의 중복 폼 전송도 처리 중에는 받지 않는다. 기존 입력 초안, 5개 기본 DB 항목, 옵션 펼침과 승인 범위는 유지한다.

[W3C 폼 알림 지침](https://www.w3.org/WAI/tutorials/forms/notifications/)의 명확한 결과, 오류가 난 항목과 복구 방법을 함께 안내하는 원칙을 적용했다. Codex/OpenCode의 위 고정 공개 소스를 다시 확인하고 [OpenCode 질문 문서](https://opencode.ai/docs/tools/#question), [Anthropic 사용자 입력 문서](https://code.claude.com/docs/en/agent-sdk/user-input)의 질문/답변/승인 계약을 재확인했다. 이 계약을 이유로 실행 권한을 확대하지 않았다. React의 기존 상태/ref와 CX Notice/Button을 재사용했으며 새 라이브러리는 추가하지 않았다.

재점검 최종 검증: 전체 런타임 순차 실행 293/293, Theia 49/49, 스킬 등록 12/12, 공유 UI 38/38, 폼 9/9와 브라우저 개발 빌드가 통과했다. 추가한 검사는 성공한 작업 뒤 목록 갱신 실패, 조회만 재시도, 앱 조회 오류 안내를 합성 응답으로 재현한다. 증적은 `verification/form-recheck-20260925/`에 있으며 실제 사용자 사용성 실험이나 실계정 DB 접속 성공을 의미하지 않는다.
