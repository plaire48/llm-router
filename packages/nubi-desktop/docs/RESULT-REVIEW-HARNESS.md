후속 개선: [하위 분석 수집과 최종 검토](ANALYSIS-HANDOFF-2026-09-25.md)는 실패한 분담과 미확인 항목을 별도 검토 입력으로 보존하고 실제 검토 진행을 작업 이력에 연결한다. 아래 217개 수치는 최초 도입 시점의 검사이며 최신 검증은 후속 기록을 따른다.

## 반영한 개선

기존 Pi 주 실행기와 읽기 전용 하위 분석은 유지하고, 최종 응답 전에 **실행 문맥과 분리된 결과 검토**를 기본 연결했다. 검토는 현재 선택한 제공자와 모델을 사용하며 도구 실행 권한이 없다.

흐름은 `요청과 근거 확인 → Pi 실행 → 독립 검토 → 누락 작업 계속 또는 정확한 결과 전달`이다. 사용자 질문이 이미 열렸다면 검토를 생략하고 기존 질문 폼을 기다린다.

- 원래 요청, 모든 완료 조건, 변경 계획의 요구사항, 사용자 답변과 이후 수정 요청을 대조한다. 장기 대화는 이미 검증된 대화 압축 경계와 최근 요청을 재사용한다. 원문은 기존 SQLite 대화 조회로 유지한다.
- 검토 입력은 주 실행기가 읽은 근거와 현재 호스트 기록이다. 하위 에이전트의 조회는 주 실행기의 수정 관찰이나 독립 검토의 직접 근거가 되지 않는다.
- Ajv가 구조, 요구사항 ID의 완전한 대응, 근거 ID의 존재와 사용 가능 여부를 검사한다. 누락이나 잘못된 JSON은 검토만 한 번 다시 요청한다. 계속 실패하면 응답을 완료 답변으로 게시하지 않고 재개 가능한 중지 상태를 남긴다.
- `supported`는 근거가 뒷받침하는 제한된 사실, `pending`은 승인이나 실행 결과 대기, `unknown`은 미확인이다. `ready`는 답변 또는 승인 대기 안내를 전달할 수 있다는 뜻이다. 완료 조건을 자동으로 통과 처리하지 않는다.
- `revise`면 같은 작업, 관찰, 요구사항과 기존 승인 경계를 유지하며 주 실행기를 이어간다. 이미 준비한 수정안을 반영됐다고 말하는 응답도 정정 대상으로 삼는다.
- 새 근거가 없는 검토 실패가 연속 3회면 기존 주관식 질문으로 필요한 조건을 확인한다. 새로운 근거가 있으면 횟수를 초기화한다. 문구, 조회어, 일시, 불투명 ID 변경과 오류는 진전으로 세지 않는다. 전체 업무의 호출 횟수 제한은 아니다.
- 검토 시작과 종료는 기존 진행 기록에 표시한다. 근거 스냅샷은 별도 SQLite 검토 기록에 저장하고 화면 상태에는 짧은 결과와 기록 키만 넣는다. 이미지 바이트는 텍스트 검토에서 제외한다.

## 검증과 한계

`tests/result-review.test.mjs`는 실제 Pi 루프, 임시 Git 프로젝트와 SQLite에 지정된 모델 응답을 연결한다. 부족한 응답의 재개, 실제 소스 조회, 수정안 승인 경계, 중복 제안 방지, 잘못된 검토, 취소, 문맥 예산, 반복 실패를 확인한다. 기존 하위 분석 테스트도 검토에 연결해 자식 조회가 주 실행기의 근거로 승격되지 않는지 검사한다.

기존 도구별 테스트는 실행 응답 시나리오와 검토 응답 시나리오를 분리한다. 공통 테스트 fixture의 기본 검토 응답은 `unknown`이며 모델 정확도 증거가 아니다. 새로운 검토 통합 테스트는 이 기본값을 끄고 실제 검토 호출과 보완 흐름을 직접 지정한다.

일반적으로 최종 답변마다 검토 호출 1회가 추가된다. 보완할 일이 있으면 주 실행과 검토가 더 이어진다. 검토 모델도 틀릴 수 있으며, 같은 모델의 별도 문맥은 독립된 정답 판정기나 실제 모델 성능 향상을 입증하지 않는다. 제공자별 실제 과제 성공률과 비용은 별도 측정 대상이다.

검토에는 최대 32개 근거와 모델 입력 예산 이내의 텍스트만 전달한다. 항목당 12,000자를 넘는 근거는 잘림을 표시하고 `supported`의 근거로 허용하지 않는다. 빠진 근거 수를 남긴다. 필수 요청과 조건 자체가 입력 예산을 넘으면 조용히 버리지 않고 멈춘다. 이미지의 시각 판단은 기존 주 실행과 읽기 전용 화면 분석이 담당하며 이번 검토는 이미지 전체를 재검증하지 않는다.

검토 기록의 ID 검증은 내용이 사실임을 보장하지 않는다. 승인 대기나 미확정 실행을 자동 실행하는 권한은 추가하지 않았다. A2A와 외부 에이전트 위임도 추가하지 않았다. 이번 소스 변경은 기존 공개 Windows 설치 파일에 포함됐다는 뜻이 아니다.

최종 로컬 검증: 전체 소스 테스트 **217개 통과**, 실제 Theia 브라우저 검사 **49개 통과**, 브라우저/Node 개발 번들 빌드 오류 0개. 세부 로그와 검사 대상 해시는 [검증 기록](../verification/harness-result-review-20260925/result.json)에 보관했다. 기존 질문 폼의 사라진 토글 버튼을 찾던 UI 검사는 현재 항상 표시되는 직접 답변 입력란에 맞춰 수정하고 새로고침 후 초안 복원을 확인했다.

## 후속 개선 2026-09-29: 실측에서 찾은 검토 반복

실모델 측정([실측 평가와 계측](LIVE-EVAL.md))에서 검토가 끝나지 않는 과제를 확인하고 아래를 고쳤다. 검토의 판정 기준과 근거 규칙은 바꾸지 않았다.

| 관찰 | 원인 | 수정 |
|---|---|---|
| 긴 Wiki 문서를 읽은 과제가 검토 10회 뒤 시간 초과로 끝남 | 읽기 결과가 12,000자를 넘어 검토 근거로 쓸 수 없었다 | `read_source`는 200줄까지 전부 돌려준다. 검토에는 줄 단위로 나눠 여러 항목으로 넘긴다(`tool:3`, `tool:3.2`). 모델의 입력 창이 작으면 다음 요청에 들어가는 만큼만 돌려준다 |
| 읽기 결과마다 프로젝트 규칙 전문이 반복됨 | 규칙 파일 내용을 읽기 결과에 매번 붙였다 | 호스트 기록의 `projectGuidance`에 있는 규칙은 경로와 해시만 남긴다. 호스트 기록에 없는 하위 폴더 규칙은 내용을 유지한다. 수정 검사에 쓰는 규칙 지문은 그대로다 |
| 200줄을 넘는 읽기 요청이 거절됨 | 범위 검사가 요청 전체를 거절했다 | 요청의 앞부분을 돌려준다. 시작 줄이 파일 길이를 넘으면 거절하고 파일 줄 수를 알린다 |
| 같은 읽기 결과가 검토 입력을 여러 번 차지함 | 근거 목록이 실행 순서 그대로였다 | 글자까지 같은 결과는 최신 1개만 넣고 `duplicateEvidence`에 수를 남긴다 |
| 매 회 새 범위를 읽어 반복 감지가 동작하지 않음 | 반복 감지는 새 근거가 없을 때만 센다 | 한 실행의 검토는 4회까지다. 4회째도 `revise`면 답변을 전달하고 검토 상태는 `revise`, 전달 사유는 `review_limit`로 남긴다. 호스트가 `ready`로 바꾸지 않는다 |
| 여러 차례 대화의 뒤 차례 답변을 첫 요청 기준으로 판정함 | 검토 입력에 현재 차례가 없었다 | 질문 답변이 아닌 최신 사용자 메시지를 `currentTurn`으로 전달한다. `request` 요구사항의 문구는 그대로 둔다 |
| 사용자 결정이 필요한데 최종 답변 글로 질문함 | 질문 도구 사용이 안내에 없었다 | 실행 안내, 보완 안내, 검토 안내에 `ask_user` 사용을 명시했다 |

검토 상한에 도달한 답변은 화면에 "보완할 결과가 있어요"와 남은 확인 항목으로 표시된다. 평가 보고서는 이 수를 `검토 상한 전달`로 따로 센다.

줄로 나눌 수 없는 결과(한 줄이 12,000자를 넘는 경우 등)는 이전처럼 잘림으로 표시하고 근거로 쓰지 않는다. B4는 읽기를 9,000자로 잘랐으나, 에이전트가 답이 있는 줄까지 읽지 않는 사례(D1)가 나와 B6에서 위 방식으로 바꿨다.

한계: 검토 입력은 여전히 근거 32개와 입력 24,000 토큰 이내다. 읽은 문서가 많으면 오래된 근거가 빠지고 검토는 그 부분을 미확인으로 둔다.

## 후속 개선 2026-09-29: 사용자가 쓴 글을 근거로 인용

gpt-5.6-sol 측정(과제 L1)에서 찾았다. 사용자가 회의록을 붙여 넣고 그 안의 결정을 정리해 달라고 했다. 모델은 도구 호출 없이 회의록에서 바로 답했다. 검토는 세 번 되돌렸고 호스트는 답을 버리고 질문을 띄웠다.

| 관찰 | 원인 | 수정 |
|---|---|---|
| 사용자가 준 글에서 나온 답이 "확인하지 못함"으로 판정됨 | 검토 입력에 글(`currentTurn`)은 있었지만 그 글을 가리키는 근거 항목이 없었다. `supported`에는 근거 ID가 필요하다 | 근거 항목 `user`를 둔다. 요청, 현재 차례, 정정, 질문 답변을 가리킨다. 글은 다시 싣지 않는다 |
| 파일을 바꾸지 않았다는 요구사항이 "확인하지 못함"으로 판정됨 | 호스트 기록의 빈 목록을 관찰로 읽지 않았다 | 검토 안내에 "빈 목록은 그런 제안, 실행, 앱 동작이 없다는 관찰"이라고 적었다 |

`user` 항목은 사용자가 무엇을 썼는지의 근거다. 파일, 테스트, 시스템의 상태는 증명하지 않는다. 검토 안내에 그렇게 적었다.

gpt-5.6-luna에서는 이 결함이 보이지 않았다. luna는 같은 차례에 도구를 호출해 근거 항목이 생겼다.

## 후속 개선 2026-09-29: 현재 차례와 정정 전 변경안

gpt-5.6-sol의 세 번째와 네 번째 측정에서 찾았다.

| 관찰 | 원인 | 수정 |
|---|---|---|
| 네 번째 차례("코드에 반영해 줘")에서 고칠 곳만 말한 답이 전달됨(L1) | 검토는 코드 반영이 없다며 되돌렸다. 그런데 요구사항 `request`에는 첫 요청이 들어 있었고, 앞 차례에서 답했으므로 "확인됨"으로 판정됐다. 열린 항목이 계획 해석(`intent:*`)뿐이어서 호스트가 판정을 `ready`로 바꿨다 | 답하고 있는 차례를 요구사항 `turn`으로 따로 둔다. 글은 `currentTurn`에 한 번만 싣고 `turn`은 그것을 가리킨다. `turn`이 열려 있으면 호스트는 판정을 바꾸지 않는다 |
| 금액 정정 뒤에 정정 전 변경안이 승인 대기로 남음(L3) | 호스트 기록의 변경안은 경로와 해시만 있어 정정 전 것인지 알 수 없었다 | 마지막 사용자 메시지보다 먼저 준비된 변경안에 `beforeLatestUserMessage`를 붙이고 안내(`proposalNote`)를 더한다. 호스트가 스스로 철회하지는 않는다 |

검토가 새 근거 없이 세 번 되돌리면 답을 전달한다(사용자 결정 2026-09-29). 검토 상태는 `revise`, 전달 사유는 `review_stalled`로 남고 화면은 "보완할 결과가 있어요"와 남은 확인 항목을 보여 준다. 검토 4회 상한(`review_limit`)과 같은 방식이다. 이전에는 답 대신 질문을 띄웠고, 질문 글에 검토가 실행기에 준 지시가 그대로 들어갔다. 평가 보고서는 이 수를 `검토 반복 전달`로 센다.
