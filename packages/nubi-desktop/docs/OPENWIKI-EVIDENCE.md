# OpenWiki를 변경 근거로 사용하는 방법

누비 Desktop은 Wiki에서 관련 규칙을 찾고, 현재 코드에서 확인한 뒤 변경 계획에 연결합니다. 문서를 읽었다는 사실과 요구사항 충족, 실제 테스트 통과를 구분합니다.

## 반영한 흐름

1. 요청에 맞춰 OpenWiki, docs, openspec을 검색합니다. 문서 제목과 구간의 제목을 함께 사용합니다.
2. `.nubi/knowledge.yaml`의 업무 용어와 별칭으로 연결된 Wiki도 찾습니다. 기존 Graphology 조회를 재사용하며 두 단계 안의 선언된 관계만 사용합니다.
3. MiniSearch 순위와 관계 검색 순위를 RRF로 합칩니다. 코드와 출처를 확인해야 하는 문서는 결과에 남기되 후순위로 표시합니다.
4. 기존 OpenWiki Claims의 문서 해시와 `repo://` 출처 버전을 현재 파일에 대조합니다. 출처의 실제 코드는 주 실행기가 다시 읽습니다.
5. 변경 계획의 요구사항에 검색 결과의 `evidenceIds`를 연결합니다. 호스트는 현재 실행에서 조회한 ID만 인정합니다. 문서, Claims, 관련 코드가 바뀌면 계획 기록과 변경 제안 시 재조사를 요구합니다.
6. 사용자가 작업을 Wiki에 기록하면 사용한 문서, 연결한 요구사항, 관찰한 버전도 함께 남깁니다. 기존 문서는 보존하고 새 버전을 만듭니다.

Windows 동작에 연결한 Wiki 근거는 제안 시, 승인 처리 시, 가상 포인터와 문서 확인이 끝난 입력 직전에 다시 대조합니다. 그사이 문서나 Claims 또는 참조 코드가 바뀌면 native 입력 없이 보류하고 새 근거와 제안을 요구합니다. 마지막 파일 읽기와 OS 동작 사이까지 원자적으로 묶는다는 의미는 아닙니다.

화면의 **소스와 Wiki**에서 업무 용어나 파일 이름을 검색하면 Wiki 근거와 출처 상태를 확인할 수 있습니다. 기존 누비 CX 구성요소를 사용하며 별도의 검색 모드 설정은 없습니다. 파일을 열어 본문과 근거를 확인합니다.

## 상태의 의미

| 표시 | 확인한 사실 |
|---|---|
| 출처 버전 일치 | Claims의 문서 해시와 버전이 현재 파일과 일치함. 주장 자체의 참이나 실행 성공을 뜻하지 않음 |
| 코드 변경됨 | Claims가 참조한 코드의 현재 버전이 달라짐 |
| 문서 변경됨 | 현재 문서가 Claims에 기록된 문서 해시와 달라짐 |
| 출처 확인 필요 | 파일 누락, 접근 제외, 잘못된 Claims 등으로 대조할 수 없음 |
| 최신성 미확인 | 버전이 없는 frontmatter 출처 또는 출처 정보가 없는 문서. 확인된 사실로 승격하지 않음 |

OpenWiki의 줄 범위 resolver는 내용이 그대로인 구간이 다른 줄로 이동해도 버전을 유지할 수 있습니다. 따라서 `repo://...#Lx-Ly`는 위치 힌트입니다. 수정하려면 현재 코드 구간을 `read_source`로 다시 읽어야 합니다. 전체 코드 파일이 계획 이후 바뀌면 보수적으로 재검토합니다.

문서 해시 불일치 표시는 Desktop의 재검토 기준입니다. OpenWiki 자체의 Claims 의미 판단이나 자동 재생성을 대신하지 않습니다. Claims sidecar는 읽기만 합니다.

## 검토한 방법론과 도입 판단

| 근거 | 실제 적용 | 이번에 넣지 않은 부분 |
|---|---|---|
| [Anthropic Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval) | 검색 구간에 제목과 문서 문맥 유지. 정확한 코드 식별자는 BM25로 검색. 검색 성공을 별도 평가 | 모델이 생성한 구간 문맥, 임베딩, 유료 reranker는 미도입. 논문의 성능 수치를 누비 성능으로 사용하지 않음 |
| [Anthropic Context Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) | 필요한 시점에 관련 문서만 조회하고 경로와 버전을 따라 현재 코드 확인. 근거가 부족하면 좁혀 재검색 | 전체 Wiki를 매 호출에 붙이거나 요약을 원문 읽기 권한으로 사용하지 않음 |
| [RRF 공식 설명](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion) | 서로 다른 검색 점수를 직접 비교하지 않고 `1 / (60 + 순위)`를 합산. 같은 문서 구간 중복 제거 | Elasticsearch 서버나 라이선스 의존성은 추가하지 않음 |
| [LangChain retrieval 흐름](https://docs.langchain.com/oss/javascript/deepagents/retrieval) | 검색, 근거 확인, 답변 검증을 나누는 설계를 검토 | 기존 Pi와 문맥 관리가 있어 추가 agent 실행기는 도입하지 않음 |
| 저장소의 OpenWiki Claims와 repository resolver | 문서와 출처 버전, 범위 이동 처리, 경로 경계를 기존 소스로 검증 | 별도 Claims 형식이나 의미 검증 엔진을 만들지 않음 |

MiniSearch 7.2.0과 Graphology 0.26.0은 기존 MIT 의존성을 재사용합니다. OpenWiki의 MIT Claims 검증을 번들에 포함하면서 해당 패키지에 고정된 Zod 4.4.3도 함께 사용합니다. Zod의 원문 라이선스는 `vendor/licenses/Zod-LICENSE.txt`에 보존했습니다. 새 서버, 임베딩 계정, 사용자 설치 작업은 추가하지 않았습니다.

## 범위와 비용

- Wiki 검색은 선언된 관계만 읽습니다. 검색할 때마다 DB를 연결하거나 SQLite 스키마를 재수집하지 않습니다. 실제 DB 정보는 기존 `knowledge_query`가 담당합니다.
- 최대 문서 400개와 본문 4 MiB를 읽고 후보 12개를 대조합니다. 출처 대조 64건, 문서당 주장 24개와 주장당 출처 12개로 제한합니다. 결과는 최대 5개, 문서당 2개, 본문 합계 10,000자입니다. 빠진 범위는 표시합니다.
- `.openwikiignore`와 Desktop의 비밀 파일 제외 규칙을 지킵니다. 읽을 수 없는 출처를 다른 파일로 추정하지 않습니다. 범위 resolver의 내부 버전 대신 짧은 해시만 모델에 전달합니다.
- 누비가 생성한 같은 작업의 기록은 기본적으로 최신 버전만 검색합니다. 에이전트가 과거 비교를 위해 `includeHistory: true`로 조회할 수 있습니다. 사람이 작성한 다른 문서는 이 필터로 숨기지 않습니다.
- 하위 분석의 Wiki 조회는 주 실행기의 계획 인용 권한이나 수정 관찰이 아닙니다. 주 실행기가 직접 조회해야 합니다.
- 사용자가 선택한 요구사항과 인용 ID의 연결을 검증합니다. 모델이 인용을 빠뜨렸는지, 인용한 문장이 요구사항을 의미적으로 뒷받침하는지까지 자동 판정하지는 않습니다. 원래 완료 조건과 실제 결과 검증은 계속 필요합니다.
- 자동 Wiki 재생성, 벡터 검색, 대형 저장소 인덱스 캐시, 실제 Qwen 답변 정확도 평가는 후속 범위입니다. 현재 변경은 Desktop에 적용하며 웹 확장과 Office의 실행 권한이나 인증 경로를 바꾸지 않습니다.

## 검증

`tests/wiki-evidence.test.mjs`는 실제 임시 Git 파일로 출처 일치, 코드 변경, 문서 수정, 파일 누락, 구간 이동, 제외 규칙, 비밀 파일과 외부 심볼릭 링크, 이력 필터, 계획 인용, 제안 전 변경 거부, Wiki 기록을 검사합니다. Pi는 합성 모델로 도구 연결을 검사합니다.

작은 고정 평가에서 같은 문서 집합과 질문 6건을 사용했습니다. 기존 BM25가 정답 문서를 상위 5개에 포함한 건수는 3건, 개선 검색은 6건이며 개선 검색의 첫 결과가 모두 정답 문서였습니다. 추가로 무관한 질문 1건은 결과가 없었습니다. 세 업무 용어 질문은 사람이 선언한 별칭과 Wiki 관계를 이용하므로 이 결과를 임의의 저장소나 자연어 전체로 일반화할 수 없습니다.

이 평가는 검색과 변경 감지의 검증입니다. 실제 사내 모델 답변의 정확도 향상, Windows 실행, 실서비스 성공을 측정한 결과는 아닙니다. 최신 실행 로그와 화면 검증 범위는 [VERIFICATION.md](VERIFICATION.md)를 따릅니다.
