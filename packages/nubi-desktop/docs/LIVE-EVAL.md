# 실측 평가와 계측

누비 workspace의 품질과 비용을 실제 모델로 측정하는 틀이다. 설계는 `docs/superpowers/specs/2026-09-29-nubi-desktop-live-eval-design.md`, 실행 방법은 [eval/README.md](../eval/README.md)를 따른다.

## 구성

| 부분 | 위치 | 제품 포함 |
|---|---|---|
| 계측 | `runtime/run-metrics.mjs`, `runtime/recovery.mjs`, `runtime/agent.mjs` | 예 |
| 평가 실행기 | `eval/` | 아니오 |
| 과제와 정답 | `eval/cases/` | 아니오 |
| 고정 자료 | `eval/corpus/` | 아니오 |

## 계측이 남기는 것

기존 SQLite `events` 표에 세 종류를 남긴다.

| 종류 | 내용 |
|---|---|
| `metric_model` | 호출 목적, 시도 번호, 요청 크기, 추정 토큰, 실제 사용량, 지연, 종료 사유, 호출한 도구 이름 |
| `metric_tool` | 도구 이름, 주 실행기와 하위 분석의 구분, 지연, 결과 크기, 이미지 수, 오류 코드 |
| `metric_compaction` | 압축 원인, 전후 추정 토큰 |

대화 본문, 도구 인자, 도구 결과 내용은 저장하지 않는다. 오류는 정해진 형식의 코드만 남긴다. 30일이 지난 계측은 다음 실행을 시작할 때 지운다. 기록에 실패해도 실행은 계속한다.

호출 목적은 `actor, planner, reviewer, summary, analysis, document`다. 호출 지점이 직접 표시한다.

## 지표

| 지표 | 계산 |
|---|---|
| 독립 통과 | 결과가 `passed`인 과제 수 |
| 답변 전달 | 작업이 `review`에 도달하고 답변이 있는 과제 수 |
| 잘못된 완료 | 작업이 `review`이고 검토가 `ready`인데 채점이 실패한 과제 수 |
| 불필요한 질문 | 질문하지 않아야 하는 과제에서 질문한 수 |
| 필요한 질문 누락 | 질문해야 하는 과제에서 질문하지 않은 수 |
| 고정 비용 비중 | 시스템 안내와 도구 정의의 글자 수를 전체 요청 글자 수로 나눈 값 |
| 캐시 비율 | 캐시 토큰을 입력 토큰으로 나눈 값 |
| 추정 오차 | 실제 입력 토큰을 추정 토큰으로 나눈 값. 사용량을 받은 호출만 계산 |

단일 가중 점수는 만들지 않는다.

### gpt-5.6-sol 측정

더 강한 모델로도 쟀다(사용자 결정 2026-09-29). 좋은 모델에서도 실패하면 하네스나 도구 호출의 문제로 본다. 조건은 위와 같고 모델만 `gpt-5.6-sol`이다. OpenWiki 위임 호출은 따로 센다.

| 지표 | luna, B5 | sol, B7(S7) | sol, B8(S8) | sol, B8c(S9) | sol, B8h(S14) | sol, B10(S16) |

| 독립 통과 | 16 | 18 | 16 | 18 | 19 | 19 |
| 답변 전달 | 17 | 18 | 18 | 19 | 18 | 18 |

sol은 같은 과제에 주 에이전트 호출을 luna의 절반 이하로 썼다. Wiki 전체 검토(D2, S3)는 두 모델 모두 위임 150회 안팎이다.

sol에서도 통과하지 못한 과제와 원인:

L1의 마지막 질문은 하네스 결함이 아니다. 시행일을 조건으로 넣을지는 사용자가 정할 일이다. sol은 S9에서 같은 점을 답변 글로, S11에서는 질문 도구로 물었다.

결정 뒤 D3와 L1을 다시 쟀다(S12).

| D3 | 확인 필요, 기준 수정 뒤 통과 | `*_BASE_URL`을 README 근거로 답했다. "`HTTPS_PROXY`를 설정하라는 안내는 없다"는 부정문에 처음 넣은 확인 표시 규칙(말로 설정을 권하는 경우)이 걸렸다. 그 규칙을 빼고 `HTTPS_PROXY=`처럼 값을 넣으라고 할 때만 표시한다 |

L1의 반복은 변경 권한의 안전 규칙에서 나왔다. 압축 전에 읽은 내용은 압축 뒤 변경의 근거가 될 수 없었다. 거절될 때 읽은 결과는 압축된 대화에 원문 그대로 남아 있었다. 사용자 결정(2026-09-29)으로 압축된 대화에 원문 그대로 남은 읽기는 근거로 인정한다(B8h). 요약되거나 참조로 바뀐 읽기는 여전히 인정하지 않는다.

B8h 뒤 다섯 과제를 다시 쟀다(S13).

| 과제 | 결과 | 내용 |
|---|---|---|
| L1 | 통과 | 압축 12회. 시행일을 `ask_user`로 물었고 가상 사용자가 답했다. 변경안 3건을 만들고 숨은 검사를 통과했다. 요약으로 넘어간 범위를 고치려 한 거절이 2번 있었고, 모델은 다시 읽고 이어 갔다 |

gpt-5.6-sol로 L1이 통과한 첫 측정이다.

B8h로 과제 20개를 다시 쟀다(S14, 위 표의 마지막 열). 19개가 통과했고 L1만 오류(`context_input_too_large`)로 끝났다. 압축한 요청이 창에 들지 않아 같은 요약을 일곱 번 되풀이했고, 답하는 메시지가 보호 목록에서 빠졌다. B9는 들지 않을 때 보호 메시지를 큰 것부터 요약에 넘기고, 첫 요청과 답하는 메시지는 남긴다.

B9로 L1을 다시 쟀다(S15). 다시 `context_input_too_large`로 끝났다. 원인은 따로 있었다. 공유 실행기는 요청마다 첫 시스템 메시지 끝에 단계 안내(약 5,000자)를 붙인다. 검토가 되돌리면 Desktop은 직전 요청을 이어서 실행하는데, 그 요청에는 이미 안내가 붙어 있어 다음 요청에 두 벌이 갔다. 되돌릴 때마다 한 벌씩 늘었다.

| 측정 | 안내가 겹친 요청 | 겹친 과제 | 더 보낸 글자 |
|---|---:|---|---:|
| S9 | 9 | S2(최대 네 벌), W4 | 66,570 |
| S14 | 21 | C2, L1, S2, S3, W3, W4 | 143,245 |
| S15 | 2 | L1 | 10,589 |

비용으로는 S14 전체 요청 글자의 0.5%지만, 22,000 토큰 창에서는 대화가 들어갈 자리를 차지했다. B10은 이어서 실행할 대화에서 붙은 안내를 떼어 요청마다 한 벌만 가게 한다(`tests/review-continuation.test.mjs`).

B10으로 과제 20개를 다시 쟀다(S16, 위 표의 마지막 열). 19개가 통과했고 잘못된 완료는 없다. 안내는 모든 요청에 한 벌만 갔다. L1을 빼면 S14와 거의 같다(주 에이전트 호출 204와 203, 위임 호출 441과 413). L1은 이번에는 시간 한도(20분)로 끝났다. 변경 계획이 이번 실행의 Wiki 근거를 인용했는데, Wiki 조회 결과가 창을 채워 압축이 일어났고, 압축이 이번 실행의 Wiki 근거를 모두 지워 계획이 `wiki_evidence_required`로 거절됐다. 모델은 Wiki를 다시 조회했고 다시 압축됐다. 이 순환이 약 스무 번 이어져 압축(요약 한 번에 약 27초)이 24번 일어났다.

B8h 결정(압축된 대화에 원문 그대로 남은 읽기는 근거로 인정)을 Wiki 근거에도 적용했다(B12). 압축된 대화에 `wiki_query`나 `ask_openwiki` 결과가 원문 그대로 남아 있으면 그 근거 ID를 다시 인정한다. 요약되거나 비워진 결과는 인정하지 않는다. 근거는 쓰는 순간에 페이지 해시, Claims, 출처 버전을 다시 검사하므로 오래된 근거는 여전히 거절된다(`tests/compaction-wiki-evidence.test.mjs`).

B12로 L1을 다시 쟀다(S17). 통과했다. 압축은 16번 있었지만 `wiki_evidence_required` 거절은 없었다. 주 에이전트 호출 58회, 위임 22회, 866초로 과제 중 가장 비싸다. 22,000 토큰 창에서 코드를 고치는 차례는 여전히 압축이 잦다.

B14로 대화 과제를 다시 쟀다(S19). L2, L3는 통과했고 L1은 `context_input_too_large`였다. 앞 실행 근거의 원문 앞부분이 호스트 기록을 약 2,200자 늘렸다. 좁은 창에서는 ID와 위치만 보이게 한 뒤(B15) L1은 통과했다(S20, 호출 57회, 위임 4회). 그 뒤 B16과 B18(새 실행에 앞 실행의 결론과 제약을 넘김)에서도 L1, L2, L3가 모두 통과했다(S21, S23).

읽는 법:

- B3은 위임을 처음 넣은 후보다. 세 과제가 Wiki 전체 검토에 호출 한도를 다 썼고, 검색 결과 제한이 한 파일 안 검색에도 적용되는 결함이 있었다.
- 과제당 1회 측정이다. 같은 후보를 다시 재면 결과가 달라질 수 있다.
- 이 모델 세션은 사용량을 돌려주지 않는다. 입력 토큰과 캐시 비율은 측정하지 못했다.
- B6부터 평가 조건이 두 가지 바뀐다. 위임 호출을 따로 세고, D3와 W3의 정답 목록이 넓어진다. B5 이전과 통과 수를 비교할 때 이 차이를 함께 본다.

## OpenWiki 갱신

`eval/wiki-update.mjs`로 쟀다(S18, gpt-5.6-sol, 후보 B13 직전, 2026-09-30). 주문 서비스 자료에서 OpenWiki가 같은 실행기와 Desktop 모델 연결로 Wiki를 만들고(준비), 제주와 도서 추가 요금을 4,500원에서 5,500원으로 바꾸는 커밋 뒤 Desktop의 갱신 흐름을 돌렸다.

| 단계 | 결과 |
|---|---|
| 준비: Wiki 생성 | 페이지 11개, 모델 호출 46회, 8분. 거절된 응답 1번은 다시 요청해 넘어감 |
| 생성 직후 상태 | 최신(`current`) |
| 원본 변경 뒤 상태 | 오래됨. 바뀐 원본 2개(`src/shipping.mjs`, 테스트), 근거가 바뀐 페이지 5개 |
| 갱신 실행(복사본) | 모델 호출 41회, 7분. 파일 15개 변경(페이지와 Claims). `AGENTS.md`, `CLAUDE.md`는 반영하지 않는 파일로 표시. 거절된 응답 1번은 다시 요청해 넘어감 |
| 반영 | `openwiki/` 아래 파일만 작업 공간에 옮김. 커밋은 하지 않음 |
| 반영 뒤 상태 | 오래됨. 한 페이지의 근거가 "원본 없음". 같은 흐름을 다시 돌린 진단에서는 최신 |
| 내용 | 바뀐 다섯 페이지 모두 5,500원을 적었다. 4,500원이 남은 곳은 레거시 정산 상수(`LEGACY_REMOTE_EXTRA`)를 설명하는 맞는 내용이다 |

찾아 고친 것:

| 문제 | 원인 | 조치 |
|---|---|---|
| 첫 실측이 `response_invalid`로 멈춤 | 모델 연결은 도구 호출이 8개를 넘는 응답을 거절한다. 계획 에이전트가 파일을 한꺼번에 읽으려 했다 | 요청마다 상한을 알림(B11) |
| 두 번째 실측도 멈춤 | 모델 연결은 글도 도구 호출도 없는 빈 응답을 거절한다. `submit_plan`이 받아들여진 뒤 모델이 빈 응답으로 끝냈다 | 거절되면 "도구 호출이 필요 없으면 한 문장으로 답하라"를 붙여 두 번까지 다시 요청(B11, B13) |
| 반영 뒤 한 페이지가 "원본 없음" | 유력한 원인: OpenWiki가 복사본의 `AGENTS.md`에 덧붙인 관리 구역을 Claims가 인용했다. 그 파일은 반영하지 않으므로 작업 공간에는 그 줄이 없다. 작업 공간을 지운 뒤라 확인하지는 못했다 | 반영 전에, 반영하지 않는 파일을 인용하고 작업 공간 버전으로는 맞지 않는 근거의 페이지를 카드에 알림(B13) |

한계: 1회 측정이다. 자료가 작다(원본 11개). 거절된 응답은 두 실행 모두 한 번씩 있었고 모두 다시 요청해 넘어갔다.

## OpenWiki 에이전트의 비용

Wiki 질문은 OpenWiki 에이전트가 자기 문맥에서 조사한다. 검색 방식과 결과 형식은 OpenWiki의 것을 그대로 쓴다(사용자 결정 2026-09-29).

| 질문 | OpenWiki 호출 | 조사 시간 |
|---|---:|---:|
| 사실 하나(K1, 기본 포트 등) | 5~9 | 12~35초 |
| 여러 문서에 걸친 질문(W2, W3, W4) | 12~18 | 50~90초 |
| Wiki 전체 검토(D2, 46만 자) | 약 150 | 약 5분 |

일반 질문에서 조사원은 2명이 병렬로 일한다. Wiki가 24,000자를 넘으면 OpenWiki가 반대 근거를 찾는 조사원을 하나 더 둔다.

## 한 응답의 여러 호출

B5 측정에서 주 에이전트가 요청한 도구 호출은 252회였다. 그중 61회는 실행되지 않았다. 단계 실행 규칙이 한 응답에서 첫 호출만 실행하기 때문이다. 61회 중 46회는 읽기 뒤에 요청한 읽기였다. B7부터 부작용이 없는 읽기 13개는 한 응답에서 모두 실행한다. 수정, 제안, 질문, 앱 조작, 위임은 이전처럼 하나씩 실행한다.

## 빌드 상태

2026-09-30 기준 `npm run compile`, `npm run build`, `npm run test:ui`, `npm run test:shared-ui`와 단위 검사 552개가 통과한다. 앱 번들에 계측이 들어 있다. OpenWiki 갱신 실행기는 `lib/backend/openwiki-update/`에 따로 있고 갱신할 때만 불러온다.

기준 HTML은 성공 색으로 초록 `#148A5C`, `#E6F6EE`를 쓴다. 공유 `agent-deck.css`는 브라우저 누비의 결정에 따라 두 값을 파랑으로 둔다. Desktop은 공유 파일을 바꾸지 않고 `design/workspace-identity.css`에서 기준 HTML의 값을 되돌린다. `scripts/check-identity.mjs`는 Desktop 계층이 값을 정하면 그 값을, 아니면 공유 값을 기준 HTML과 대조한다.

## 한계

- 문자열 검사는 예상하지 못한 표현의 정답을 놓칠 수 있다. 실패한 과제는 `result.json`의 답변을 직접 읽어 확인한다.
- 과제가 20개다. 두 보고서의 차이는 관찰이며 우열의 입증이 아니다.
- 압축 과제는 모델의 문맥 한도를 22,000 토큰으로 낮춘 조건이다. 실제 사내 모델의 한도와 다르다. 압축 품질은 `eval/compaction.mjs`로 따로 잰다.
- 합성 자료에는 Claims가 없다. 검색 결과는 항상 미검증으로 표시된다.
- 새 Git 저장소로 시작하므로 Wiki 생성 커밋이 작업 공간에 없다. 커밋 기준 최신성은 측정하지 않는다.
